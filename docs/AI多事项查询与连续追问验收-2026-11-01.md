## 可直接尝试

| 场景 | 输入与预期 |
| --- | --- |
| 多事项查询 | “我的未缴账单，以及充20度电要多少钱”应返回账单和报价两项结果；“我的未缴账单，同时查我的已发布成绩”应同时处理两类查询。 |
| 逐步补充 | 同一会话依次输入“我想充值”“电费”“20度”。先询问水电种类，再询问金额或用量，最后按当前宿舍电价报价；示例 0.61 元/度时为 12.20 元。 |
| 可选条件 | 缺少信息时显示“电费”“水费”或示例金额／用量按钮。点击只填入输入框，用户仍需发送查询。只有当前最新结果显示补充按钮。 |
| 防止漏查 | 一次超过四类查询，或同一工具出现不同条件（如“充20度电；充30度电”），提示拆分；相同查询重复出现则去重。 |
| 历史关联 | 先查账单列表，再问“第二笔为什么这么贵”，保存当时解析到的具体账单关联；即使之后列表发生变化，恢复这条历史提问仍指向原账单，并重新检查本人权限。 |
| 旧历史保护 | 旧的序号或指代提问没有保存明确关联时，点击重新查询会提示进入具体业务页面选择事项，不覆盖当前输入，也不按最新列表猜测。普通历史问题仍可重新查询。 |

“同时容纳20人”等场地要求中的描述词不会被当成多事项分隔符，校区、人数和时间条件保持在同一查询中。

## 连续追问的边界

- 补充条件只在同一用户、同一会话的最近一次待补充充值查询中合并。切换其他话题会清除待补充状态，其他会话不能继承。
- 仅合并明确的水电种类、数字及单位，不猜测缺失金额或用量。水电两种类型混在一个不明确的报价请求中会要求澄清。
- 补充条件在本地合并；即使使用 DeepSeek 模式，也不需要把先前对话发送给模型，响应会标记本次是否实际调用模型。
- 每次报价重新读取当前入住、表计和价格；不创建订单、不支付、不退款。业务操作继续在原页面完成。
- V41 为 `agent_turn` 新增可空的解析上下文及待补充报价字段，保留原请求上下文和账单引用。重复请求仍按原请求比较，避免派生上下文导致重试冲突。
