# 校园支付开源组件调研与接入方案

日期：2026-10-30。

后续进展：演示账单和支付宝沙箱支付入口已开发，最新状态见[支付宝沙箱演示缴费接入](./支付宝沙箱演示缴费接入-2026-10-30.md)。本文保留调研及接入前方案。

状态：当前已选用并引入 `IJPay-AliPay:2.9.13`，补充其所需的旧 Servlet 运行时类型依赖，使用不传递 Servlet 对象的核心接口。本文保留组件调研及早先官方 SDK 编译记录；最新验证见 [IJPay 兼容性与基础接入](./IJPay兼容性验证与基础接入-2026-10-30.md)。收费业务尚未实现，未发起沙箱或真实资金交易。

## 1. 建议

采用“统一缴费账单 + 支付渠道适配”的方式。当前首个渠道组件已确定为 IJPay 的支付宝模块，后续在自己的沙箱应用中联调。需要微信渠道时，再验证并引入 IJPay 微信模块；本次未引入 `IJPay-All`。Vue 页面由本项目实现账单、收银和结果查询。

开源 SDK 解决签名、验签和支付接口调用，账单、授权、业务定价、退款审批及对账仍由本项目实现。开源组件不能替代支付平台应用和商户配置。

## 2. 当前项目哪些地方适合支付

源码核对结果：目前没有账单、支付订单、退款或余额台账。现有住宿、调宿、报修、预约表及请求对象没有收费金额、计费单位或收费规则字段。因此，目前没有可直接启用收款的既定收费事项。

原需求在 [需求规格说明书 v0.2](./需求规格说明书-v0.2.md) 第 63、70、500 行分别把收费、电费支付和支付列为扩展项。本次用户提出新增支付，应另行补齐这些业务规则；这些旧范围描述不构成拒绝新增功能的理由。

| 已有模块 | 当前实现 | 可增加的支付场景 | 接入前需要补齐 |
| --- | --- | --- | --- |
| 校园报修 | 派单、维修、结果验收和评价 | 明确需要收费的耗材或有偿服务 | 有权限人员报价、费用明细、本人确认、撤销和退款规则；不能把所有报修默认改为收费 |
| 场地与设备借用 | 申请、审核、使用登记、核销及取消 | 明确配置为收费的场地或设备 | 价格版本、按次或按时计价、支付期限、资源保留时间、取消退款规则；押金须单独建模 |
| 我的住宿与调宿 | 入住、退宿、调宿及宿舍报修 | 住宿费或经确认的费用差额 | 收费期间、收费标准、付款义务人、换宿差额和退费规则 |
| 水电缴费 | 没有计量、账户或充值接口 | 后续宿舍水电账单或充值 | 宿舍账户、计量与计费数据、学校服务接口、入账确认和失败补偿；不能仅凭支付成功显示充电成功 |
| 学费、校园卡充值 | 没有对应业务 | 单独新增服务后可接入 | 财务账单来源或校园卡余额台账，以及收款后实际入账接口 |
| 请假、在校证明、学习查询 | 已有办理或查询流程 | 当前没有收费依据 | 保持现有流程；有明确新收费规则后再扩展 |

以上是根据现有代码提出的候选场景，不是对学校实际收费制度的判断，也不代表已决定向这些业务收费。

建议先建统一缴费中心，允许受授权岗位发布有业务来源和明确金额的账单；首批选择有偿维修或收费借用中的一个场景完成全过程，再扩展住宿收费。不得先编造宿舍费率、维修单价或校园卡余额。

## 3. 开源组件比较

查询对象均为 Java 服务端开源组件，与当前 Maven 工程的集成方式一致。下列项目的仓库元数据或 POM 标注 Apache-2.0；实际引入时保留所选发布包的许可证及依赖声明。

| 组件及来源 | 能力 | 本项目的适用性 |
| --- | --- | --- |
| [支付宝官方 Java SDK](https://github.com/alipay/alipay-sdk-java-all) | 支付宝接口、请求签名与响应验签；同时提供 v2、v3 协议版本 | 直接调用的备选，也是 IJPay 支付宝模块的底层依赖。早先对 v2 SDK 相关 API 做了隔离编译验证 |
| [微信支付官方 Java SDK](https://github.com/wechatpay-apiv3/wechatpay-java) | 微信支付 APIv3；包含 Native 扫码支付、通知解析等接口 | 微信渠道备选。只做支付时无需引入完整微信生态组件 |
| [WxJava](https://github.com/binarywang/WxJava) | 微信支付、公众号、小程序、企业微信等，支付模块为 `weixin-java-pay` | 未来同时接微信公众号或小程序时值得采用；仅支付场景可只引 Pay 模块。不能把其旧 Spring Boot 示例或 Starter 的可用性等同于 Boot 4 已验证 |
| [IJPay](https://github.com/Javen205/IJPay) | 支付宝、微信、银联、PayPal 等多个渠道的封装 | 当前选型。支付宝模块 2.9.13 使用核心接口并补充旧 Servlet 运行时类型；Web 层继续使用 Jakarta |
| [pay-java-parent](https://github.com/egzosn/pay-java-parent) | 多渠道、多账户的支付 SDK 与简单 Web 示例 | 可作备选；首批单一校园收款场景使用官方 SDK 更直接。本次没有对它做编译或支付验证 |

截至本次检索：支付宝 v2 官方 README 和 Maven Central 的发布版本为 `4.40.1061.ALL`；微信官方 README 和 GitHub Release 使用 `0.2.17`。本次验证固定这两个版本，不以浮动版本引入。

IJPay 的 GitHub 开发分支 POM 仍显示 `2.9.12.1`，Maven Central 已发布 `2.9.13`。WxJava 的开发分支、GitHub Release 和 Maven 时间戳版本也不是同一种版本口径。不能仅从仓库首页的版本文字判断实际应引入的发布包。

版本与接口资料：

- [支付宝 v2 SDK README](https://github.com/alipay/alipay-sdk-java-all/blob/master/v2/README.md)。
- [微信支付 SDK README](https://github.com/wechatpay-apiv3/wechatpay-java#readme)。
- [支付宝 Maven 元数据](https://repo.maven.apache.org/maven2/com/alipay/sdk/alipay-sdk-java/maven-metadata.xml)。

## 4. 已核实的兼容性和验证边界

### 官方 SDK 隔离编译

在仓库忽略的 `artifacts/payment-research-2026-10-30/` 建立独立 Maven 工程，未修改后端生产 POM、业务代码或数据库。

验证环境：Temurin 21.0.11、Maven 3.9.11、Spring Boot 4.0.8、`spring-boot-starter-webmvc`，编译目标 Java 21。依赖同时引入：

```xml
<dependency>
  <groupId>com.alipay.sdk</groupId>
  <artifactId>alipay-sdk-java</artifactId>
  <version>4.40.1061.ALL</version>
</dependency>
<dependency>
  <groupId>com.github.wechatpay-apiv3</groupId>
  <artifactId>wechatpay-java</artifactId>
  <version>0.2.17</version>
</dependency>
```

编译覆盖支付宝网页支付请求、RSA2 通知验签、查单和退款调用，以及微信 Native 下单、使用 `jakarta.servlet.http.HttpServletRequest` 提取通知头并交给官方通知解析器的调用。运行 `compile dependency:tree` 返回 `BUILD SUCCESS`。

证据：

- `artifacts/payment-research-2026-10-30/pom.xml`。
- `artifacts/payment-research-2026-10-30/src/main/java/cn/zzuit/research/PaymentSdkCompatibility.java`。
- `artifacts/payment-research-2026-10-30/build.log`。
- `artifacts/payment-research-2026-10-30/dependencies.txt`。

本次仅确认依赖可解析、上述 API 在该最小工程中可编译。没有执行示例方法、启动支付服务、进行 SDK 网络请求或校验真实平台通知；没有证明与校园后端全部依赖共同运行时的兼容性。

依赖树显示，支付宝包传递引入了 Fastjson `1.2.83_noneautotype`、Bouncy Castle `1.62`、dom4j `1.6.1`、OkHttp `3.12.13` 等版本。后续正式引入前需审查和对齐传递依赖，并运行双渠道通知解析与原工程回归。本次没有据此做漏洞扫描，也不对这些版本作安全性结论。

### IJPay 发布包核对

本次下载并读取 Maven Central `IJPay-AliPay:2.9.13` 的 POM 和源码包：

- POM 声明 `javax.servlet:javax.servlet-api:4.0.1`，作用域为 `provided`。
- `AliPayApi.java` 导入 `javax.servlet.http.HttpServletRequest` 和 `HttpServletResponse`。
- 包含接受旧 `HttpServletResponse` 的网页支付方法，同时也有返回字符串的重载。

当前校园工程使用 `jakarta.servlet.*`。这是类型不匹配的实际证据，不能直接把当前响应对象传入这些旧接口；这也不意味着 IJPay 的所有工具方法均不可用。选择 IJPay 时应单独验证不依赖 Servlet 的调用方式和运行时类加载。

后续实际验证发现，即使使用返回字符串的 `tradePage` 重载，编译也会因同名重载需要解析旧 Servlet 类型而失败；改用 `pageExecute` 后仍需旧 Servlet 类型完成 IJPay 类加载。当前工程已经采用“`pageExecute` 核心接口 + `javax.servlet-api:4.0.1` 仅运行时依赖”的方式，具体证据与验证范围见 [IJPay 兼容性与基础接入](./IJPay兼容性验证与基础接入-2026-10-30.md)。

发布包证据：[2.9.13 POM](https://repo.maven.apache.org/maven2/com/github/javen205/IJPay-AliPay/2.9.13/IJPay-AliPay-2.9.13.pom)、[2.9.13 源码包](https://repo.maven.apache.org/maven2/com/github/javen205/IJPay-AliPay/2.9.13/IJPay-AliPay-2.9.13-sources.jar)。对应仓库源文件：[AliPayApi.java](https://github.com/Javen205/IJPay/blob/dev/IJPay-AliPay/src/main/java/com/ijpay/alipay/AliPayApi.java)。

## 5. 建议的最小业务闭环

1. 有权限的业务岗位根据明确收费规则发布账单，记录业务来源、应付人、项目明细、金额和版本。
2. 用户在本人账单页核对费用后主动发起支付。后端重新核验本人归属和账单状态，从数据库取金额并生成商户订单号。
3. 后端通过渠道适配器构造支付请求。页面展示渠道返回的受控收银入口，支付完成返回后查询本系统状态。
4. 服务端收到通知后先验签，核对应用、收款商户、商户订单、币种及金额，再依据渠道交易状态处理。前端跳转或“我已支付”按钮不能直接把账单置为已付。
5. 支付订单、账单、业务结果和通知记录在事务中幂等更新。相同通知重复到达、查询与回调同时执行，均不得重复入账或重复执行后续业务。
6. 通知缺失时由服务端查单补偿。支付超时、关单、业务取消与付款并发必须有明确处理；无法确认渠道结果时显示处理中。
7. 已付款业务取消进入退款处理，保存独立退款单和渠道状态，查询确认结果。业务退款规则应在启用收费前完成。

支付宝通知参数核对与返回要求参考[平台通知文档](https://developer.alibaba.com/docs/doc.htm?articleId=105902&docType=1&treeId=193)；微信通知解析参考[官方 SDK](https://github.com/wechatpay-apiv3/wechatpay-java#readme)。具体协议以选定支付产品的当前官方文档为准。

### 数据与权限

- 在 `cn.zzuit.campus.payment` 增加领域模块，分离账单、支付订单、渠道通知和退款单。业务账单与某次渠道付款尝试分别保存，重试不能重复生成应付义务。
- 金额以人民币分整数持久化，调用支付宝时使用精确十进制转换；前端只提交账单标识，不能自行决定价格。
- 业务来源和收费版本建立唯一约束，保存应付人及价格快照。账单发布后的修改使用作废重开等明确流程。
- 增加本人支付和岗位账单管理等独立权限。管理员、宿管、辅导员或维修人员不能因现有身份自动取得全部财务资料或退款权。
- 账单详情、支付记录、退款记录和下载均复用实时身份检查及本人／岗位范围校验。
- 通知入口仅对指定渠道路径和 HTTP 方法开放，并只对相应服务端通知端点豁免 CSRF；本人发起支付、查单操作和后台管理沿用当前鉴权规则。平台通知以签名及订单核对认证，不能依赖用户登录会话。
- 消息关联需同步扩展 `user_notice` 来源约束和 `NoticeService` 的入口检查，避免只新增消息文字却没有有效业务链接。
- Agent 首期可提供本人账单状态及原页面链接；支付确认、退款确认和平台密钥不交由模型处理。

### 页面与现有业务衔接

- 增加“我的缴费”：待缴、处理中、已缴及退款记录、账单详情和支付结果。
- 增加受权限控制的费用办理页面，明确账单来源和金额明细。
- 现有报修、借用、住宿详情通过有权限的账单标识关联统一缴费中心；免费业务不因接入支付新增等待付款状态。
- 场地如采用审核后付款，须定义付款前保留时段、到期释放及迟到通知的处理；不得在未定义退款规则时收取押金。
- 水电或校园卡后续接入时，将“支付已成功”和“外部账户已入账”分别展示并补偿失败，不能直接把两者视为同一状态。

## 6. 环境准备与后续验收

支付宝沙箱需要同一应用的 App ID、应用私钥、支付宝公钥及沙箱网关等配置，参考[支付宝开放平台接入说明](https://open.alipay.com/paymentServicer/paymentProvider.htm)。当前网关以沙箱控制台显示为准，旧示例地址不能直接作为项目最终配置。密钥在服务端通过环境变量或仓库外文件加载。

微信官方 SDK 列明商户号、商户 API 私钥、APIv3 密钥等前置条件，具体验签材料按平台公钥或证书模式配置，参考[官方前置条件](https://github.com/wechatpay-apiv3/wechatpay-java#%E5%89%8D%E7%BD%AE%E6%9D%A1%E4%BB%B6)。开源 SDK 本身不提供商户资格或可用账户。

本地默认后端只监听 `127.0.0.1:7080`，第三方平台无法直接访问。平台通知联调需要可访问的测试回调地址及明确转发到本地对应环境的方式；在此之前，可用受控替身测试签名、金额和状态处理，但不能报告为平台回调已验收。

接入时至少验收：

- 正常付款、本人归属、越权读取及停用后权限失效。
- 金额或应用／收款商户不匹配、无效签名、伪造跳转参数和重复参数。
- 双击付款、重复通知、并发查单、通知延迟、超时与响应丢失。
- 渠道未明确关闭前禁止盲目创建另一笔可支付订单，避免同一账单多次扣款；跨渠道切换需确认旧单已关闭。
- 已付后取消、重复退款、退款失败、退款查询补偿及事务回滚。
- 免费业务回归、现有预约取消和使用阶段、消息链接、窄屏及键盘操作。
- 隔离 H2 的迁移和集成测试，MySQL 迁移与关键唯一约束复核。
- 本人账单到渠道支付再返回的浏览器验收，平台真实沙箱通知及查单验证。

实施前尚需确定的是首批实际收费事项及账单来源，以及可用的支付平台测试应用。这些不是开源组件能自动推导的信息。
