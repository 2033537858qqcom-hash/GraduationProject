# 校园角色功能调研与开发优先级 v0.1

调研日期：2026-10-05。学校背景：郑州工业应用技术学院。目的：为现有 Java / Vue 3 工程补充实际业务，明确学生、任课教师和工作人员分别使用什么功能，以及推荐的开发顺序。

同日开发更新：用户确认后已交付师生与教务的首批教学功能，见[教学功能迭代验收](./教学功能迭代验收-v0.1.md)。本文第 3 节保留调研时、开发前的缺口快照，不作为当前工程完成清单。

本文是调研与开发建议，不把其他高校的制度写成郑州工业应用技术学院的制度，也不把功能原型写成已开发的系统。现有需求仍以[需求规格说明书 v0.2](./需求规格说明书-v0.2.md)、[核心业务流程与验收](./核心业务流程与验收-v0.2.md)和[学生端教学查询补充](./学生端教学查询补充-v0.1.md)为基线。下文“新增候选”尚未纳入这些基线，不另造已覆盖的需求编号。

## 2. 用户与岗位分别需要哪些功能

下表是本项目的角色功能建议。身份是“我是谁”，岗位是“我有权处理什么”；一人可以兼任多个岗位，但每次处理仍必须验证对应权限与数据范围。

| 身份或岗位 | 核心功能 | 数据范围 | 当前范围定位 |
| --- | --- | --- | --- |
| 学生 | 本人课表、课程资料和通知、已发布成绩与考试；请假、在校证明、报修、住宿；活动社团、预约、个人日程、我的事务 | 本人记录、有效教学班资料、授权公共服务 | 主要已在基线中，待实现完整业务 |
| 任课教师 | 本人课表、授课课程与教学班、学生名单、课程资料、班级通知；本人预约、报修与办理进度 | 本人授课关系与本人事务，不能因此读取全校学生私有信息 | TCH、FND、MSG、RES、FIX 等基线 |
| 辅导员／学生事务办理岗位 | 负责行政班的学生目录、学生申请审核、补交材料、班级通知、待办与处理记录；后续可补充销假、资助材料初审 | 所负责行政班及获授权事项，任课关系不等于学生事务审核权 | 审核与通知已在基线；销假、资助为新增候选 |
| 教务人员／学院教学秘书 | 学期、课程、教学班和授课关系维护；课表、考试、成绩的受控导入与发布；后续调停课审核与成绩更正流程 | 授权学院、学期、课程与岗位动作 | FND、CAL、EDU-Q 已在基线；完整教务流程为候选 |
| 后勤派单人员 | 工单分诊、信息补充、派单、改派、取消申请处理、超时跟进、区域与类别统计 | 所负责校区、区域与维修类别 | FIX、FLW 基线 |
| 维修人员 | 分配给本人的工单、接单、维修进度、完成说明与图片、无法维修反馈 | 本人获分配工单；无权浏览所有学生资料 | FIX 基线 |
| 宿管／住宿管理人员 | 楼栋、房间、床位状态，入住与退宿；调宿申请审核、人工安排、关联报修 | 所负责楼栋及住宿事项 | DOR、FND 基线 |
| 场地与设备管理人员 | 开放时间、维护时段、预约审核、使用登记、设备借还、损坏处理、逾期跟进 | 所负责资源 | RES、FLW 基线 |
| 社团负责人／活动组织者 | 社团资料、成员申请、活动申请与发布、报名名单、签到、取消与成果 | 本人负责的社团或活动；不自动取得场地审批权 | CLUB、ACT 基线 |
| 官网编辑／审核人员 | 新闻公告、栏目与学校公开资料维护、预览、送审、审核、发布、撤下 | 所负责内容；编辑与审核权限分别授予 | ADM 基线，当前实现部分流程 |
| 平台管理员／运维 | 账号、角色、组织与岗位配置，导入、审计、系统配置；备份、私有文件、知识索引与模型用量维护 | 管理与运维权限；业务审批、私有申请材料权限另授 | IAM、FND、OPS、ADM 基线，当前实现部分基础 |
| 图书、财务、人事、就业等专门岗位 | 初期提供经核验的办事指南与入口；将来分别评估借阅、费用查询、报销、人事申请、就业手续等办理能力 | 各专门系统与职责范围 | 集成或后续模块候选，不算已接入 |
| 访客、考生、校友 | 学校公开信息、招生与就业介绍、校区位置、公开活动、联系渠道；入校预约等另行评估 | 公开信息；无在校身份的本人受理事项需单独授权设计 | 官网基线；专用办事为候选 |

### 学生端栏目建议

保留已有校园门户方向，按[学生端教学查询补充](./学生端教学查询补充-v0.1.md)的六个栏目组织：

1. **我的校园**：今天的课、重要消息、待本人处理事项、常用服务、申请进度摘要。
2. **我的学习**：课表、课程资料、教学班通知、成绩、考试安排。
3. **学生办事**：请假、在校证明、材料补交与办理指南。
4. **活动预约**：活动报名、社团申请、场地设备预约、取消与签到。
5. **校园生活**：我的住宿、报修、校园位置、已开放的生活服务。
6. **我的事务**：跨模块申请记录、状态、处理意见、结果、撤回与反馈。

首页只展示摘要。成绩明细、材料上传、审批表单、资源管理等放在对应独立页面；没有上线的事项显示“指南”或“规划中”，不能伪装成可办理的按钮。

### 教师与岗位工作台建议

- 任课教师首页突出今日授课、本人教学班、需要维护的课程资料与教学通知。
- 辅导员工作台突出负责班级、待审核申请、待补交和超时事项。
- 维修人员工作台突出待接单、处理中和需要继续处理的工单。
- 资源与宿管工作台突出各自资源及待处理事项。
- 同一账号兼任任课教师和辅导员时，可切换工作台；后端按实际动作、关系与状态验证，不依赖前端切换授予权限。

## 4. 推荐开发顺序

这是依据当前工程的开发顺序建议，不是已完成的里程碑。相比最初文档以活动为首个闭环的顺序，本轮建议先补齐师生日常学习，再推进事务；纳入迭代计划时同步更新相关流程、字段和验收。

| 迭代 | 交付功能 | 对应现有需求 | 完成时应该能够演示什么 |
| --- | --- | --- | --- |
| 1：师生教学基础 | MySQL 联调；账号组织与岗位维护；学期、课程、行政班与教学班、授课关系；学生周课表、课程资料与通知；教师授课工作台；授权教务维护考试与成绩查询数据 | IAM、FND、CAL-01、TCH、MSG-04/05、EDU-Q01—03、OPS-01 | 教务维护演示教学数据，教师发布本人班资料与通知，正确学生查看，其他班不能访问；学生只看到本人已发布成绩考试 |
| 2：学生办事闭环 | 服务目录与指南；请假、在校证明；草稿、提交、补交、撤回、审核、结果；辅导员岗位、统一事务和待办 | CAT、SVC、HOME、MSG、FLW | 学生提交后由对应负责岗位处理，学生可查意见与结果；无审核岗位的任课教师不能审批 |
| 3：校园生活闭环 | 报修、派单、维修、本人确认与评价；住宿基础、调宿与人工入住处理 | FIX、DOR、FLW | 学生或教师报修，派单员分配，维修员处理，申请人确认；调宿后床位与本人住宿记录一致 |
| 4：活动与资源 | 资源开放维护、预约冲突与审核、设备借还；社团、活动申请、报名、签到、取消与通知 | RES、CLUB、ACT、CAL、MSG | 教师或社团组织活动，经过资源和活动审核，学生报名签到；同一时段资源不能重复占用 |
| 持续推进：Agent | 迭代 1 后先做带来源的制度查询和本人课表查询；迭代 2 后接入本人事务查询与申请草稿；后续受控确认提交 | AGT、ADM-02、OPS-04/05 | 问题能落到实际信息或本人业务；草稿可核对，提交后有实际记录、待办和状态反馈 |

第一迭代内部可分两次交付：先完成授课关系、师生课表与课程资料通知，再完成教务信息维护及本人成绩考试查询。两个交付都复用同一身份与组织模型，不一次堆满门户首页。

### 后续新增候选如何选择

| 候选 | 建议位置 | 增加前要解决的具体问题 |
| --- | --- | --- |
| 请假销假 | 学生办事后的小迭代 | 当前基线“审批通过即可完成”需改为请假执行与返校确认；补齐拒绝、延期、未按时销假等状态和验收，不默认按缺勤处罚 |
| 教师调停课 | 教学基础之后 | 课程周次、节次、教师与教室冲突；谁审批；批准后如何同时更新师生课表和通知 |
| 教师成绩录入 | 教学查询之后 | 只录本人教学班、录入窗口、成绩构成、送审锁定、发布岗位、更正审计；不能把查询补充误解为已允许所有教师改分 |
| 教学评价、选课 | 教学基础稳定之后 | 评价可见性、重复提交；课程容量、时间冲突、选退课窗口与重修关系 |
| 资助、就业与毕业离校 | 可选后续业务 | 各阶段材料与处理岗位、名单可见范围、跨部门完成项与撤回规则 |
| 图书、财务、人事 | 先指南与入口，后评估集成或自建 | 可用接口、身份授权、数据同步、回调、失败处理；无接口时仅做明确标注的演示，不能声称实际已对接 |

先把当前已设计的模块做出闭环，再按价值补充候选。完整校园平台可以由统一身份、入口、事务与若干完整业务模块组成，专业系统的入口或集成也是合理组成部分。

## 5. Agent 对各类用户的价值

以下是项目能力设计，不是宣称现有学校门户已具备这些 Agent 功能。

| 用户 | 先实现的能力 | 边界 |
| --- | --- | --- |
| 学生 | 查本人课表、课程位置和申请进度；解释材料与规则；引导对应页面、生成申请草稿 | 本人成绩等敏感信息由本人主动查询；提交需核对后确认，不能自行批准 |
| 任课教师 | 查本人授课安排与教学班；整理资料发布步骤与通知草稿 | 首期课程资料和通知仍在正常页面发布，遵守 TCH 与既有 Agent 边界 |
| 辅导员与管理岗位 | 定位本人待办、解释缺少的材料、辅助归纳处理记录 | 不跨班级读取材料，不替代岗位人员作出审批决定 |
| 后勤与维修岗位 | 查询获授权工单、解释处理步骤、协助填写处理说明 | 接单、转派、完成等动作必须落到同一个业务接口和合法状态 |
| 平台运维 | 知识索引状态、工具执行情况、用量与失败定位 | 运维权限不自动授予学生私有材料阅读权限 |

Agent 与页面共用业务服务和权限，不另建一套可绕过规则的工具接口。知识回答标明来源、更新时间和适用范围；学校公开制度与项目演示规则分开检索和说明。右下角角色的页面建议在角色授权内生成，可关闭或暂停，不主动展示成绩、请假原因等私有详情。

## 6. 第一批功能的验收重点

1. 两名学生登录后课表、资料、考试与成绩按本人和有效教学关系隔离。
2. 两名教师只能维护本人有效教学班资料与通知；移交或授课关系失效后不再能操作原班级。
3. 行政班与教学班分别存储，同一个教学班可以包含多个行政班学生；辅导员与任课教师的授权关系分别存储。
4. 授权教务人员在职责范围内导入与发布演示数据；错误批次不发布，未发布成绩不展示为零分，考试变更同步查询与提醒。
5. 服务目录区分可办理、仅指南和未开放；本人事务、岗位待办与普通通知各自反映真实业务状态。
6. 新增请假模块按现有基线完成申请与处理；若采用销假等候选，先同步需求与状态验收，不在实现中隐式改变完成标准。
7. 接口直接验证身份、岗位、数据范围与业务状态；隐藏菜单不能代替授权，角色停用与撤权后访问失效。
8. 文件下载按所属业务授权；材料不会因放到公开资源目录而被其他账号访问。

开发验证覆盖这些跨角色和状态规则；本次只交付调研与计划，不把上述验收写成已经测试通过。
