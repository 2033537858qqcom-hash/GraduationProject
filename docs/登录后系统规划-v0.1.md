# 登录后系统规划 v0.1

日期：2026-09-30。

本文补充现有需求，将官网之外的系统定位为校园一站式服务系统。原有业务仍有效，新增模块仅为建议，未自动纳入必做范围。

## 1. 公开资料参考

- [深圳大学学生入口](https://www.szu.edu.cn/jsrk/xs.htm)将学习工具、办事大厅和生活事务组织为不同服务入口。
- [深圳大学办事大厅](https://ehall.szu.edu.cn/new/index.html)公开页面包含服务、收藏、待办、流程跟踪和未读消息等结构。
- [浙江大学服务平台](https://service.zju.edu.cn/_s2/cs_bszx/main.psp)支持按主题和部门查找服务，并区分不同师生群体。
- [复旦大学在校学生入口](https://www.fudan.edu.cn/407/list.htm)覆盖学习、学生事务和生活服务。

这些来源只用于观察公开服务分类与导航，没有登录上述系统，不代表已经核验其内部实现。公开学生入口不等于登录后的实际工作台。

## 2. 系统定位

官网负责学校形象与公开信息；登录后的系统负责个人校园事务、服务办理、工作人员处理和智能辅助。

系统以用户身份与当前事务组织信息，包含统一工作台、服务中心、业务模块、处理工作台和管理后台。不能仅将不同管理列表放在同一个菜单下作为集成成果。

## 3. 第一层：统一个人工作台

- 今日安排：课程、考试通知、活动和预约；没有考试数据时不凭空生成考试安排。
- 我的待办：待补材料、待确认维修、待归还设备；有审核权限时显示待处理申请。
- 我的申请：统一查询当前状态、处理意见、时间线和结果文件。
- 我的报名与预约：状态、取消规则及详情。
- 消息中心、服务收藏、常用服务和最近使用。
- Agent 入口：跨服务咨询、查询和办理辅助。

学生以个人事务为主，教师增加组织和被授权的审核入口，服务人员增加其负责岗位的任务。多角色账号使用同一身份和消息，可切换工作视图，不重复注册账号。

## 4. 第二层：服务中心

服务中心是现有功能的统一入口，不是额外建设一种业务。

- 按服务主题、办理部门、适用身份搜索和筛选。
- 每个服务有说明、适用人群、必需材料、流程、处理时限、负责部门与办理入口。
- 收藏常用服务，显示服务是否开放和维护状态。
- 登录用户仅看到有权限办理的入口；允许显示不适用事项的公开说明时，明确不能办理。
- 服务详情引用维护中的规则，普通页面与 Agent 使用相同版本。
- 草稿、提交记录、审批、结果文件与日程统一关联。

## 5. 第三层：业务分区

### 5.1 现有范围的组织方式

| 分区 | 用户功能 | 工作人员功能 |
| --- | --- | --- |
| 学习与日程 | 课表导入、课程安排、个人任务、冲突提醒；考试通知可由已发布内容关联 | 学期与节次配置、课表维护、考试信息发布 |
| 学生事务 | 请假、证明申请、补交材料、撤回、结果下载 | 所属学生申请审核、办理反馈与历史 |
| 活动与社团 | 社团加入、报名、签到、成员及主办活动管理 | 入驻与活动审核、成果维护 |
| 空间与设备 | 查询、预约、领用、归还、取消 | 资源维护、审核、使用登记、异常处理 |
| 后勤服务 | 报修、进度、确认、评价 | 分诊、派单、处理、改派 |
| 消息与个人记录 | 日程、待办、消息、申请时间线 | 对应岗位处理记录与必要提醒 |

现有范围不包括成绩、选课、学籍、缴费业务。学习类的信息展示不自动扩展为完整教务系统。

### 5.2 可扩展候选

以下是让校园服务覆盖更广的候选，加入前应估算工时并补齐流程与验收。

| 候选 | 可控实现范围 | 不默认扩展的部分 |
| --- | --- | --- |
| 宿舍服务 | 本人住宿信息、宿舍相关报修、调整申请与人工处理 | 全校自动排床、门禁、电费支付 |
| 图书服务 | 演示馆藏、个人借阅、续借申请、归还及到期提醒 | 接入真实图书馆、真实借阅设备 |
| 学生发展 | 一类奖项申报或竞赛项目申报、材料审核、结果发布 | 真实资助发放、复杂综合测评 |

候选业务若采用演示模块，应具备真实可运行的状态与记录，不能用不能办理的空入口充数。若暂未实现，则不展示为已上线服务。

## 6. 第四层：工作人员处理与管理后台

### 6.1 工作人员处理

职责是处理分配的业务任务，不天然拥有系统管理权。

- 教师：本人组织的活动、被指定的申请审核。
- 社团负责人：所负责社团成员、活动与资源申请。
- 资源人员：负责资源的审核、开放、维护与借用归还。
- 学生事务人员：所属事项和学生范围内的申请。
- 后勤派单人员：分诊、派单和改派；维修人员仅处理已分配任务。

### 6.2 管理后台

- 基础目录：校区、学院、专业、班级、学期、部门、建筑与场地。
- 身份组织：学生与教师身份、班级归属、教师审核关系、社团负责人、岗位范围。
- 服务目录：事项说明、适用人群、材料清单、流程、部门与时限。
- 业务管理：审核、资源维护、报修派单和处理记录。
- 内容与知识：官网栏目、公开资料、内部指南、知识版本及可见范围。
- 平台运营：统计、权限、审计、提醒规则与必要配置。

基础目录需覆盖已实现业务所需字段，不要求建设独立人事或学籍系统。账号角色、身份关系和数据范围分开定义。

## 7. Agent 如何融入

Agent 在同一权限范围内组合查询和业务工具，每项操作遵循普通页面规则。

| 请求例子 | 关联业务 | 可产生的结果 |
| --- | --- | --- |
| 这周有哪些没处理的事？ | 课表、预约、报名、申请、待办 | 带来源链接的事务清单与时间冲突说明 |
| 给社团准备一场分享活动 | 活动、场地、设备、指南 | 结构化申请草稿，确认后提交联合申请 |
| 请假需要什么材料，帮我准备申请 | 办事指南、学生归属、申请 | 条件说明、材料检查、申请草稿 |
| 我的报修为什么还没处理？ | 工单、派单与处理记录 | 当前实际状态、处理时间线及负责岗位信息 |

模型不直接读写数据库，不审批、不派单、不编造记录。用户确认后再次检查权限、时间与资源；重复提交、超时未知结果和失败处理见现有流程文档。

复杂任务以界面显示的步骤、草稿、确认和记录为成果，不以聊天窗口数量或模型自行报告的成功为验收依据。

## 8. 系统导航建议

用户工作台：个人首页、服务中心、学习日程、活动社团、资源预约、校园办事、后勤报修、我的事务、消息、智能助手。

工作人员工作台：我的任务、负责的业务、处理历史、岗位通知；按实际职责显示。

管理后台：基础数据、账号权限、服务配置、官网内容、各业务管理、知识管理、统计审计。

菜单按身份裁剪。业务列表、详情、审批和 Agent 共享稳定业务标识，详情可从不同入口访问但始终校验权限。

## 9. 需求补充顺序

1. 先落实基础目录、组织归属、服务中心、不同角色的工作台和统一申请记录。
2. 现有六类业务按原计划完整实现。
3. 评估宿舍、图书、学生发展候选的投入，决定是否纳入后续版本。
4. 设计角色导航与页面原型，再形成实体关系与接口契约。

完善系统应优先检查身份、办理规则、工作人员处理、状态历史、消息和日程是否闭环；新增业务数量不是唯一指标。
