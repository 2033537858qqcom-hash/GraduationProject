# 角色职责与任务流转审查及整改方案

日期：2026-10-17。范围：当前 Java／Vue 工程的身份、角色权限、组织和负责关系、业务任务、工作台和 Agent。本文是基于源码、数据库迁移和现有测试的静态审查及建议方案，未调整实际账号、授权或数据库，也未将下列问题宣称为已完成修复。建议分工属于毕业设计方案，不代表学校已确认的现行岗位制度。

核心判断：已有按班级、学院、楼栋、维修负责范围鉴权的基础，可以保留。主要问题是基础身份与业务岗位混用、多岗位入口策略不统一、不同业务的数据范围和交接规则不一致，以及“能打开模块”没有形成“谁负责当前任务”的完整模型。预约模块存在优先修正的后端授权边界问题，不能只改菜单。

## 1. 目前实际有哪些角色

迁移脚本共定义 12 个角色：STUDENT、TEACHER、SERVICE_STAFF、ACADEMIC_STAFF、COUNSELOR、STUDENT_AFFAIRS、REPAIR_DISPATCHER、REPAIR_TECHNICIAN、DORM_MANAGER、CONTENT_EDITOR、CONTENT_REVIEWER、ADMIN。访客通过公开接口访问，无需建立访客登录账号。

当前不完全是“学生／教师／管理员”三分法：账号可叠加角色；辅导员有行政班负责关系；证明按学院；宿管按楼栋；维修按负责范围和当前派单。角色数量本身并非主要问题。

应继续保留的基础：

- `IdentityService.requirePermission` 与 `LiveIdentityFilter` 重新读取有效账号和权限，安全版本变化会使旧会话失效。
- 请假审核排除草稿、本人申请和非负责班级；证明审核排除草稿、本人申请和其他学院。
- 维修已经区分申请人、派单人员、维修人员和本人验收，并限制当前范围及分配关系。
- 调宿初审按学院，床位操作按楼栋；附件另行鉴权，宿管不因岗位身份获得附件下载权限。
- 官网内容有编辑与审核动作及禁止自审机制。

证据：[实时鉴权](../backend/src/main/java/cn/zzuit/campus/identity/LiveIdentityFilter.java)、[请假](../backend/src/main/java/cn/zzuit/campus/leave/LeaveService.java:43)、[证明](../backend/src/main/java/cn/zzuit/campus/certificate/CertificateService.java:58)、[调宿材料](../backend/src/main/java/cn/zzuit/campus/housing/HousingTransferService.java:33)。

## 2. 已发现的问题与处理优先级

P0 表示应在继续扩展该业务前处理；P1 表示角色和任务重构的首批内容；P2 表示后续业务深化。未经过接口复现的问题在此保持静态核查结论，不等同于已验证所有运行配置下的实际结果。

### R01：预约把“维护资源”扩展成“查看和取消任意申请”（P0，代码可直接确认）

`getDetail` 和 `cancel` 将 `reservation:review` 或 `reservation:manage` 均视为通用工作人员权限，没有进一步核对校区、资源归属、本人关系或草稿隐私。V25 又把 `reservation:manage` 直接授给 ADMIN。因此系统管理员仅凭资源维护权限，就能够通过相应接口读取他人预约详情，并在状态允许时取消他人预约；详情包含申请人、学工号、联系方式和用途等字段。

同时，`listReview` 的基础条件为 `WHERE 1=1`，没有资源负责关系或学院／校区范围约束，也没有基础排除他人草稿。`updateVenue` 只要求维护权限，同样没有“我负责哪些场地”的判断。

解决：拆分 `reservation:read_own`、`reservation:review`、`reservation:cancel_managed` 与 `resource:maintain`；增加资源负责人／管理团队与作用范围。资源维护权限不推出申请阅读、审批或业务取消权限。工作人员只读取职责范围内已提交的申请；草稿原则上只归本人。取消还须区分申请人取消、资源负责人因停用取消等动作，记录原因并通知受影响者。

证据：[详情授权](../backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:280)、[取消](../backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:570)、[审核列表](../backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:610)、[默认授予](../backend/src/main/resources/db/migration/V25__venue_reservations.sql:90)。

### R02：预约未校验禁止自审，通知收件人也不按资源路由（P0，代码可直接确认）

`review` 检查审核权限和 SUBMITTED 状态，但没有排除申请人本人。账号可以同时持有 TEACHER 与 STUDENT_AFFAIRS，前者得到申请权限，后者得到审核权限；当前校验组合存在自行提交并审核的路径。

提交通知查询全体具有 `reservation:review` 的启用人员，然后 `LIMIT 5`；没有按资源、校区或具体职责过滤，也没有保证通知的就是本单应处理的人。问题不是五个人太少，而是没有先确定负责人。

解决：所有入口统一执行“操作者不得审核自己的申请”；兼岗也不能绕过。提交时先解析资源负责范围，再把任务加入对应岗位队列。团队处理可以通知全部有效候选人，也可以通知已指定承办人；不得无规则截取前五个账号。没有有效负责人时保留草稿并提示配置缺口，不伪装为已进入正常办理。

证据：[预约审核](../backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:645)、[通知选人](../backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:534)、[兼岗校验](../backend/src/main/java/cn/zzuit/campus/foundation/FoundationService.java:119)。

### R03：多岗位被固定优先级压成一个首页身份（P1，已确认的界面／架构问题）

工作台标题按管理员→辅导员→学生事务→教师→教务等顺序取第一个；登录落地页和页头又使用自己的优先级。菜单则继续累加权限入口。因而兼任教师和辅导员的人虽然仍能访问教学页面，首页却只把他当作辅导员。学生身份与工作岗位叠加时，学生导航分支还会取代岗位首页链接。

解决：一个账号保留多个已授权工作空间，如“个人服务／教学工作／班级事务”。首页显示当前工作空间、负责范围和对应待办，可以显式切换。切换只选择当前上下文，不产生新的权限；后端仍重新核对该岗位、范围与业务状态。

证据：[工作台标题](../frontend/src/pages/WorkbenchPage.vue:23)、[落地页](../frontend/src/stores/auth.ts:47)、[页头和导航](../frontend/src/layouts/PortalLayout.vue:25)。

### R04：岗位首页主要还是服务入口，缺少完整的任务汇总（P1，代码可直接确认）

`/api/workbench/overview` 的 `tasks` 固定返回空列表，仅汇总请假和证明数量；维修通过另一个请求补充。预约审批、调宿初审、待派床、待入住、官网待审核等，没有形成同一任务列表。模块内部有队列，不等于工作台已接通。Agent 的 `my_review_pending` 也只汇总请假和证明。

解决：新增任务聚合接口，先调用各领域已有的受限队列，不立即引入通用流程引擎。首页显示“待我处理、待补充、等待他人、即将超时”，以及任务类型、当前节点、申请人必要信息、负责范围、截止时间和操作入口。岗位首页与 Agent 共用任务提供器；未读消息不作为待办数量来源。

证据：[空任务列表](../backend/src/main/java/cn/zzuit/campus/portal/PortalController.java:56)、[首页数据读取](../frontend/src/pages/WorkbenchPage.vue:25)、[Agent 待办](../backend/src/main/java/cn/zzuit/campus/agent/AgentTools.java:237)。

### R05：学生事务、系统管理员和资源管理的职责交叉（P1，权限配置及设计问题）

STUDENT_AFFAIRS 已同时承担证明、调宿初审、全局借用审批和资源维护；ADMIN 自动得到官网编辑／审核、教室资源、住宿配置、报修配置和预约资源维护等能力。并非每项均为越权漏洞，但业务数据维护与平台技术管理没有分清。

预约的维护 API 已存在，前端却没有相应资源维护入口与完整页面：当前前端未找到 `reservation:manage` 的展示判断或更新资源表单。于是“授了权限但没有可完成的岗位任务”。

解决：保留学院事务人员处理学院学生事项；新增一个“资源管理岗位”模板，用负责资源集合区分图书馆、报告厅、体育场等，无需为每栋楼再建一个新角色。宿舍和报修的业务配置逐步交给对应业务负责人。系统管理员默认负责账号、授权配置、系统配置和技术审计，业务岗位单独明确授予。审核与维护拆开后，由业务负责人维护本范围的资源和开放规则。

来源：[初始管理员权限](../backend/src/main/resources/db/migration/V2__public_catalog.sql:14)、[预约授予](../backend/src/main/resources/db/migration/V25__venue_reservations.sql:90)、[预约维护 API](../backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:93)、[前端预约功能](../frontend/src/pages/ReservationPage.vue)。

### R06：调宿未分配床位阶段缺少明确的任务归属（P1，已确认行为，待确定产品分工）

待安排队列检查的是当前人员是否至少具有一个有效负责楼栋；该 EXISTS 没有关联当前申请的校区、原住宿或目标范围。因此一个有楼栋范围的宿管可以进入全部 AWAITING_ASSIGNMENT 申请池，并读取申请原因、意向和说明。预留后、入住前及已结束记录才按目标楼栋限制。这里不能笼统说“宿管可读全部附件”：材料服务已经独立禁止宿管取得附件。

共享待分配池可以是一种明确批准的业务设计，但不宜默认向所有楼栋宿管开放，当前也没有标明谁必须接单、谁负责跨校区协调。

建议分为“住宿统筹分配”和“楼栋执行”两个权限包：学院初审→按校区进入住宿统筹队列→统筹选择负责楼栋／床位→该楼栋宿管确认入住。可由一人兼任两项岗位，但普通楼栋宿管只接触执行所需信息。跨校区申请明确转交给相应统筹人员。

证据：[待安排队列](../backend/src/main/java/cn/zzuit/campus/housing/HousingTransferService.java:167)、[申请范围](../backend/src/main/java/cn/zzuit/campus/housing/HousingTransferService.java:297)、[返回说明字段](../backend/src/main/java/cn/zzuit/campus/housing/HousingTransferService.java:306)、[附件单独鉴权](../backend/src/main/java/cn/zzuit/campus/housing/HousingTransferService.java:33)。

### R07：教务归属与教学参与关系混在一起，教学职责也偏集中（P1／P2，部分属于原定范围取舍）

建教学班、增授课教师和选课学生时，参与人员必须与维护人员属于同一学院。这能支撑学院内部演示，但教学班的管理学院与参与师生所属学院是两个概念，通识课、跨学院选修和公共课会被挡住。

学院教务权限同时创建全局学期、课程，导入和发布成绩。任课教师目前只负责资料、通知和授课查询。这与原有首期范围一致，不能简单叫作安全漏洞；若目标扩大为完整教学业务，则录分、复核、发布的分工仍需补齐。

解决：保留教学班管理归属，教师和学生通过有效教学关系参与；跨学院关系由明确授权的教务建立，检索只返回建立关系所需字段。学期等校级目录由校级教务职责维护，学院负责本院教学安排。后续成绩采用“任课教师录入草稿→提交→授权教务复核发布→更正留痕”；若暂不开发录分，应继续准确标注为“教务导入成绩”。

证据：[同学院参与限制](../backend/src/main/java/cn/zzuit/campus/teaching/AcademicService.java:70)、[全局学期创建](../backend/src/main/java/cn/zzuit/campus/teaching/AcademicService.java:47)、[成绩操作](../backend/src/main/java/cn/zzuit/campus/teaching/AcademicService.java:125)、[教师接口范围](../backend/src/main/java/cn/zzuit/campus/teaching/TeachingController.java:32)。

### R08：岗位变更与人员离岗保护覆盖不一致（P1，交接风险）

账号维护对辅导员班级移交、未完成请假和证明、最后一名证明处理人员有专门保护；没有同等覆盖全部维修执行、调宿预留／入住和预约承办职责。旧会话失效是正确的，但不能代替处理剩余任务。

解决：调整岗位或负责范围前显示影响清单：当前待办、负责班级／楼栋／资源、未结束预约与预留。普通离岗执行移交或进入有负责人接管的异常队列，保留原操作者历史。紧急停用必须能立即撤销访问，同时把任务冻结或转交，不能为了维持流程而继续保留不应有效的账号权限。

证据：[账号更新和停用保护](../backend/src/main/java/cn/zzuit/campus/foundation/FoundationService.java:92)。

### R09：岗位说明、中文名称和真实权限不同步（P1，已确认）

Foundation 的学生事务范围说明仍只写证明；实际已叠加调宿和预约。DORM_MANAGER 没有对应明确说明分支。个人资料页的角色中文映射缺少宿管、后勤派单和维修角色，可能直接显示英文编码。SERVICE_STAFF 是只具工作台／通用能力的早期角色，尚未对应明确业务责任。

解决：统一岗位定义和名称来源，返回中文名称、动作权限、负责范围、职责说明、有效状态及办理入口。`SERVICE_STAFF` 作为基础教职工身份或历史兼容标签，新增授权须选具体业务岗位，不再把它描述成万能服务人员。说明和权限变化一起版本化。

证据：[角色说明](../backend/src/main/java/cn/zzuit/campus/foundation/FoundationService.java:52)、[中文角色映射](../frontend/src/pages/ProfilePage.vue:3)、[空泛服务角色](../backend/src/main/resources/db/migration/V2__public_catalog.sql:8)。

### R10：资源有多套目录，但实际使用责任没有贯通（P2，模型风险）

教室由 classroom_resource 管理，预约另有 venue_resource。当前预约资源没有关联到教学教室的统一物理资源标识；教学占用和借用冲突也分别查询。如果同一物理教室被两套目录维护，不能保证课程／考试与借用自动避冲突。这里是条件性风险，不是本次已复现了真实重复预约。

同时，“设备借用”目前主要以资源类别和文字设备需求表示，未见完整数量库存、发放、归还和验收责任链。应明确是预约服务还是完整设备借还业务。

解决：建立稳定的物理资源映射和共同占用查询，让业务负责人维护一份资源身份和可用规则。若保留“设备借还”名称，补充资源人员的发放／归还验收任务；暂不实现时准确收敛为“场地预约及附带设备需求”，避免菜单名称扩大实际能力。

证据：[预约资源模型](../backend/src/main/resources/db/migration/V25__venue_reservations.sql:1)、[预约冲突查询](../backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:140)、[教学资源占用](../backend/src/main/java/cn/zzuit/campus/resource/RoomService.java:24)。

## 3. 推荐的角色与职责矩阵

用户体验保留统一登录入口、个人服务、岗位工作台和系统管理，不为每个角色单独开发一套登录系统。岗位可以兼任，数据范围不能因兼任自动扩大。下面描述的是建议目标，新增和调整项尚未实施。

| 身份／岗位 | 主要办理责任 | 允许的数据范围 | 需明确禁止／分开的动作 |
| --- | --- | --- | --- |
| 访客 | 浏览官网、已发布信息、校园探索 | 公开数据 | 内部申请和个人记录 |
| 学生 | 学习查询、请假、证明、预约、报修、住宿与本人验收 | 本人记录及开放资源 | 自审、修改成绩和他人材料 |
| 任课教师 | 本人授课安排、教学班资料通知；后续本人课程录分草稿 | 有效授课教学班 | 自动审批学生全部事务、看其他教学班私有资料 |
| 辅导员 | 学生请假、补交和班级事务跟进 | 明确负责且有效的行政班 | 自动获得全院成绩维护、场地审核和调宿派床权限 |
| 学院事务人员 | 学院证明、调宿初审等明确授予事项 | 获授权学院、事项和阶段 | 自动维护全校资源或为其他学院办理 |
| 教务人员 | 教学关系、排课考试、成绩复核发布 | 校级目录或所管教学单位的独立授权 | 把所属学院等同于所有参与师生的学院；替教师越范围录改 |
| 住宿统筹岗位（权限包） | 按校区安排调宿目标、协调跨楼栋分配 | 指定校区和待分配池 | 对所有宿管开放全校待派床详情 |
| 楼栋宿管 | 入住退宿执行、目标床位核对、预留和入住确认 | 明确负责的楼栋；按授权拆分分配与执行 | 因楼栋身份自动阅读调宿附件或全校申请 |
| 资源管理岗位（新增模板） | 场地开放规则、负责资源审批；设备发放与归还验收 | 明确负责资源集合 | 资源维护直接推出所有申请阅读／取消权 |
| 后勤派单人员 | 分诊、派单、改派、跟踪和异常协调 | 有效校区、类别和地点范围 | 查看与办理无关的学生私有材料 |
| 维修人员 | 接单、维修反馈、交回任务和提交结果 | 当前分配给本人且范围有效的工单 | 自己替申请人验收关闭 |
| 内容编辑／审核 | 编辑送审；审核他人内容、发布撤下 | 授权栏目；本人草稿和受理稿 | 自审；自动读取学生办事 |
| 系统管理员 | 账号、授权配置、组织技术维护、系统配置与审计 | 系统管理对象 | 默认获得业务材料、审核、成绩修改或业务取消权 |

新增岗位不代表新增同等数量人员。一个业务管理员可以明确兼任资源管理或住宿统筹，但授权记录必须说明“以什么岗位、负责什么范围”。只因有 ADMIN 就默认为所有业务负责人，不作为目标设计。

## 4. 身份、岗位、范围和任务如何分开

建议分为五个概念：

1. **账号／人员**：谁在使用系统，是否启用。保留现有 app_user，不建设完整人事系统。
2. **基础身份与组织归属**：学生、教职工、长期所在学院／部门。组织归属是人员信息，不自动等于全部业务范围。
3. **业务任职**：辅导员、学院事务、资源负责人等。支持同一人兼任、开始／结束时间、停用和必要代办。
4. **负责关系**：具体学院、行政班、教学班、宿舍楼、场地、报修类别及地点。复用已有关系表，缺少的再补。
5. **业务任务**：某份申请到哪个节点、进入哪个队列、谁可以领取、谁正在办理、何时到期、下一步交给谁。

授权判断建议统一表达为：有效账号 ∧ 有效岗位 ∧ 具备动作权限 ∧ 资源在负责范围内 ∧ 业务状态允许 ∧ 不触发禁止自审／职责冲突规则。

任职可采用轻量 `role_assignment(user_id, role_code, organization_id, starts_at, ends_at, status, version)`。这是建议结构，不代表立刻替换当前全部 user_role。请假的 counselor_assignment、教学的 instructor/member、宿舍楼栋范围和维修范围先复用，增加资源负责关系。范围复杂时通过关系表表达，不把大量 JSON 条件和动态 SQL 作为首期方案。

例：某老师的长期组织归属为计算机学院，同时是软件工程 2026 级 1、2 班辅导员，并为两个有效教学班任课。他进入“教学工作”只管理授课教学班，进入“班级事务”只处理两个行政班的请假。临时代审其他范围通过有期限的额外任职授权，不靠修改老师本人所属学院实现。

## 5. 主要业务的责任流转

| 业务 | 建议责任链 | 退回／异常的责任 |
| --- | --- | --- |
| 请假 | 学生提交→当前班级辅导员处理→本人查结果；已通过生成日程 | 退回由学生补交；辅导员变更移交待办。首期保留当前一级流程，长期规则再按确认制度扩展 |
| 在校证明 | 学生核对资料提交→授权学院事务人员核对→受控结果生成→本人下载 | 无有效承办岗位保留草稿并显示配置缺口；不能由技术管理员直接代审 |
| 调宿 | 学生提交→学院初审→指定校区住宿统筹分配→目标楼栋宿管确认入住→系统原子切换住宿 | 取消、超时、原住宿变化分别进入明确处理分支；原床位释放不得脱离已核对的入住事务 |
| 场地预约 | 师生提交→该资源当前负责人处理→使用→关闭记录 | 退回由申请人补充；资源故障取消由有取消权限的负责人处理并通知；初审是否需要学院参与按具体事项配置 |
| 设备借还 | 申请→资源负责人审核→发放登记→借用人归还→工作人员验收关闭 | 缺损、延期和未归还由该资源管理岗位跟进；只做到预约时不把批准当作归还完成 |
| 报修 | 师生提交→负责范围派单人员→指定维修人员→原申请人验收→关闭 | 拒接／交回由派单人员改派；验收不通过回到维修；申请人久未验收按已确认的提醒和异常规则处理 |
| 成绩（深化项） | 任课教师录入草稿→提交→教务复核发布→学生读取已发布结果 | 更正重新审批并保留历史；首期未做教师录分时明确保留“教务导入”能力边界 |
| 官网内容 | 编辑草稿送审→有权审核的另一人处理→发布公开快照 | 退回归原编辑；更正重新走审核，不覆盖公开旧版等待状态 |

不能把“提交成功”当成“已有负责人”；不能把“审批通过”当成“设备已归还”；消息已读也不代表任务已完成。每个节点都应能回答：当前责任队列是什么、还有谁能接管、申请人下一步做什么。

## 6. 工作台和任务接口建议

首批任务接口建议为 `/api/workbench/tasks`，查询当前已授权工作空间。数据应包含 taskKey、businessType、businessId、stage、title、status、scopeSummary、candidateQueue、assignee、createdAt、dueAt、allowedActions、targetPath 和版本。列表、数量、详情入口和 Agent 的统计使用同一受限任务查询，避免列表看不见却被统计出来。

首期直接从现有领域状态派生待办，通过 `TaskProvider` 聚合，不重新建立一套与原业务状态可能矛盾的通用流程状态。只有确实需要团队领取、承办人跟踪时，再持久化领取关系。采用队列候选人→一个人领取／办理→节点结束的规则；提交动作重查权限并使用版本条件保证并发只有一次有效结果。

工作台建议显示：

- 顶部：当前工作空间、当前负责范围、岗位有效状态及切换入口。
- 主要区域：待我处理、待我补充、等待他人、即将超时，可直接打开具体任务。
- 辅助区域：已办记录、常用服务、业务说明；服务卡不代替待办。
- 系统管理空间：账号异常、无负责人队列、授权到期、资源配置缺口等，不能用“管理员查看全部业务材料”来解决排障。

Agent 复用相同工作空间、任务提供器及领域权限；具备多个岗位时明确当前以哪个岗位查询。模型不获取 ADMIN 身份，不直接修改数据库，不代替人工批准或验收。保持已有草稿预览、人工确认、恢复时重查权限和敏感数据留在本地的边界。

## 7. 可分批落地的实施顺序

### 第一批：先修有明确边界的授权缺口

处理 R01、R02：补资源负责关系、限定详情／列表／维护／取消范围、禁止自审、按真实候选队列发通知。保留原有申请、处理记录和消息；通过新迁移调整授权，不回改已经执行过的 V2／V25。盘点原 STUDENT_AFFAIRS 和 ADMIN 的预约权限，形成迁移清单，避免默认给所有人全范围授权。

此批完成标志：技术管理员不能仅凭维护权限读取申请；资源 A 负责人无法审批资源 B；申请人即使兼岗也无法自审；无负责人申请不会进入假待办。

### 第二批：统一岗位表达与工作台

处理 R03、R04、R09：统一角色名称和说明，清理 SERVICE_STAFF 的模糊定位，返回有效工作空间；接通预约、调宿、住宿执行和内容审核的任务列表。已存在模块继续提供实际处理页面，不为了改工作台重复建设业务。

此批完成标志：兼任教师／辅导员可以清楚切换；首页数量、真实列表与 Agent 一致；每条待办能说明范围和下一处理动作。

### 第三批：完善跨部门交接和业务配置归属

处理 R05、R06、R08：划分住宿统筹和楼栋执行，把资源、维修、住宿的业务配置从技术管理员默认职责中分离；完善人员离岗、职责变更、代办到期和无候选人的接管流程。

### 第四批：深化教学和资源使用闭环

处理 R07、R10：支持获授权的跨学院教学参与，区分校级和学院教务职责，按最终教学范围决定教师录分；统一物理资源映射和占用查询，补设备发放归还。不上来引入微服务拆分、复杂 ABAC 平台或通用审批流程设计器。

每批先形成范围和动作矩阵，再实现后端授权和回归，最后接页面。现有有价值的班级、学院、楼栋和维修关系应迁移复用，不推翻重写。

## 8. 必需的验收场景

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| AUTH-01 | 管理员仅有账号／资源维护权限，访问学生预约详情或取消接口 | 拒绝；不因管理员名称特殊放行 |
| AUTH-02 | 资源 A 的负责人访问／审核／取消资源 B 的申请 | 全部拒绝，列表／数量／消息也不包含 |
| AUTH-03 | 申请人兼任审核岗位，审核本人预约 | 后端拒绝，换页面、Agent 或直接请求仍拒绝 |
| AUTH-04 | 审核人员尝试查看他人未提交草稿 | 拒绝；不把草稿放入队列 |
| TASK-01 | 资源没有有效负责人 | 保留可恢复草稿并显示缺口，不虚报已经正常受理 |
| TASK-02 | 团队两人并发处理同一待办 | 只产生一次有效结论，另一人得到已处理／版本变化提示 |
| TASK-03 | 同一人兼任教师与辅导员 | 两个空间分别展示真实范围和待办，切换不获得额外权限 |
| TASK-04 | 工作台、业务队列和 Agent 查询相同任务 | 同范围、同状态、同数量，失败不能报零或成功 |
| HANDOVER-01 | 唯一承办人离岗，或岗位代办到期 | 旧访问及时失效，待办有明确接管／异常队列和审计 |
| HOUSE-01 | 普通楼栋宿管查看未交给本范围的其他校区调宿 | 按明确分工拒绝；附件限制继续保持 |
| EDU-01 | 授权教务建立跨学院公共课关系 | 能建立有效参与关系；无关系教师仍不能看其他班私有数据 |
| RESOURCE-01 | 同一物理空间已有课程／考试，又提交借用 | 共用占用查询发现冲突；不因两张资源表而放行 |
| CLOSE-01 | 设备预约获准但尚未归还 | 保留发放／归还责任，不当作已完成 |

测试数据至少需要两个学院、两个校区、两个资源负责人、一个兼岗账号和一个离岗人员；不能只依赖多数账号都挂同一学院的演示初始化来判断范围正确。现有 `VenueReservationIntegrationTest` 覆盖正常预约和生命周期，但未见针对上述资源范围和禁止自审的专门断言。

## 9. 本次建议结论

优先修预约的范围和禁止自审，再做岗位工作空间及统一待办，随后补跨部门交接与业务负责人。以“谁发起、谁处理、能看哪些数据、下一步交给谁、异常谁兜底”为每个模块的设计验收依据。审批不应只由一个角色编码决定，技术管理员也不应成为所有业务的默认处理人。
