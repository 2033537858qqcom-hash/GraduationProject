# 调宿统一办事与消息跳转验收

日期：2026-10-15。工程版本 0.1.0，数据库 V21。业务与账号为毕业设计演示，不连接学校真实住宿系统。

## 1. 本批完成

学生的“我的办事”统一查询请假、证明、报修和调宿。调宿有独立入口、种类筛选和业务状态名称，完成结果显示“查看调宿结果”。列表仅返回编号、种类、状态、版本、时间和固定详情路径，不返回原因、材料或房间信息。

| 调宿状态 | 概况归类 |
| --- | --- |
| 草稿 | 未提交草稿 |
| 待初审、待安排、待入住 | 正在办理 |
| 待补交 | 需要补充 |
| 已完成、已拒绝、已撤回、已取消、已过期 | 已结束办理 |

概况统计当前账号有权查看的全部本人记录，不随列表种类、状态或分页筛选变化。撤销业务权限后，该业务的记录与统计同时隐藏；显式访问无权限种类返回 403。访问统一办事时刷新本人的过期预留，避免把已过期记录继续计入办理中；重复读取不重复通知或释放床位。

## 2. 消息与详情

新增的调宿通知记录 `HOUSING` 来源、申请编号和固定视图。V21 仅扩展既有消息来源约束，保留请假、证明、报修和普通消息，不根据旧消息文字猜测或回填来源。

| 接收人及事件 | 详情入口 |
| --- | --- |
| 本学院事务人员：提交、补交 | `/student-affairs/housing?id=N&tab=details` |
| 学生本人：初审结果、预留、入住、取消处理、释放、期限调整、过期 | `/housing/transfer?id=N&tab=details` |
| 目标楼栋当前有效宿管：请求取消 | `/housing/assignments?id=N&tab=details` |

消息摘要保留申请编号、事件和下一步提示，不复制申请原因、材料、审核意见或完整房间。详情显示原资料和现有初审意见；宿管办理意见的完整时间线仍待后续完善。普通历史消息保持原样。

每次读取消息重新校验业务权限、本人归属、学院范围和楼栋范围；无权查看时保留消息而隐藏申请入口。消息列表的链接检查只读，不触发过期处理或产生新消息。前端仅接受三个固定调宿详情路径、正整数编号和 `tab=details`，不接受额外动作参数。

学院和宿管增加受限详情接口。学院详情同时核对审核人员学院、申请学院快照及学生当前学院，不能审核自己或查看草稿。宿管待安排队列要求至少一个有效负责楼栋；已有目标的待入住和历史记录均核对当前目标楼栋权限。取消通知只发给目标楼栋当前有效人员。

从旧消息进入时，即使记录已离开待办队列，仍能按当前权限定位并显示详情。取消请求待处理时禁用确认入住。宿管操作后同步刷新床位；已完成记录显示新住宿，不再显示旧入住截止提示。

## 4. 浏览器验收

独立内存库 18081 / 前端 18091，关闭 DeepSeek。通过 API 创建标明演示来源的楼栋、入住、已完成记录和待初审记录，浏览器实际完成：

1. 学生在统一办事筛选调宿、待初审，并打开指定申请。
2. 学院从旧消息进入已完成申请，随后审核当前待初审申请。
3. 宿管安排空闲床位，父页面床位立即显示已预留。
4. 学生从预留消息进入待入住记录，并请求取消。
5. 目标楼栋宿管从取消消息进入指定申请；确认入住禁用；同意取消后记录保留，床位释放。
6. 学生统一办事变为全部 2、正在办理 0、已结束 2；原住宿仍是 2 号床。

`ui-results.json` 核验最终状态为 `CANCELLED` 和 `COMPLETED`，目标床位 `VACANT`，宿管可读已取消历史且无办理动作。办事列表和学生调宿详情在 1440 / 1024 / 768 / 390 宽度下均无页面横向溢出；390 宽度的表格在自身区域横向滚动。视口已恢复。浏览器控制台未记录错误。

截图：`affairs-pending.png`、`affairs-results.png`、`review-historical.png`、`manager-cancel-request.png`、`affairs-mobile.png`、`transfer-mobile.png`；尺寸数据 `responsive.json`。临时验收服务完成后关闭。

## 5. 主环境与数据保留

主库使用根目录 `data/campus.mv.db`。停服后离线复制并核对 SHA256，备份清单 `backup.json`，基线 `baseline.log`：V20、入住 0、调宿 0、会话 1、任务 4、查询记录 1。此处任务数是本批开始时重新读取的值，不沿用上一批的 3。

V20 → V21 后，宿舍楼 0、本人调宿及统一调宿记录 0、原会话 1、任务 4 均保留。没有向主库写入验收住宿或调宿申请；本批真实模型调用 0 次。DeepSeek 仍按本地加密凭据配置可用。证据 `main-backend.log`、`main-checks.json`，服务保持 18080 / 18090。

`backend/data/campus.mv.db` 是保留的旧 V14 库，未切换使用。显式数据源启动方式沿用[宿舍关联报修验收](./宿舍关联报修与入住权限验收-2026-10-15.md#5-本地库与限制)。
