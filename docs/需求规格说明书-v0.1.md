# 校园综合服务平台需求规格说明书 v0.1

历史版本：当前需求以[需求规格说明书 v0.2](./需求规格说明书-v0.2.md)及其配套流程为准，本文件保留讨论记录。

编写日期：2026-09-30

性质：第一版需求设计草稿。用户已确认产品方向，本文中的模块细分、流程规则和参数为建议方案，尚未经过导师评审。本文不锁定框架版本和具体中间件。

## 1. 产品目标

构建面向虚构校园的综合服务平台，提供原创校园官网、学生与教师工作台、校园业务管理后台，以及能够查询信息和辅助办理事务的 Agent。

官网按正式学校官网设计，以学校形象和校园信息展示为主。公开新闻、校园文化、社团和建筑介绍来自平台管理的数据。用户通过统一入口登录后进入独立业务工作台，办理结果同步至个人记录、日程和消息。Agent 使用同一套业务规则和数据权限，并且仅在登录后的系统提供。

### 1.1 已确认的官网与系统边界

官网首页不是全部模块的集合页。首页仅选取校园展示内容，各栏目拥有独立列表或详情页面。登录状态不改变官网的展示定位，个人事务始终在工作台呈现。

| 区域 | 访问条件 | 内容与操作 |
| --- | --- | --- |
| 学校官网 | 无需登录 | 学校概况、新闻公告、校园风采、公开文化活动及建筑介绍 |
| 登录入口 | 无需登录 | 统一身份登录及校园服务入口 |
| 业务工作台 | 登录后且具有对应权限 | 报名、预约、申请、报修、指南、日程、待办与 Agent |
| 管理后台 | 登录后且具有岗位权限 | 内容维护、审核、派单、资源、用户、统计与审计 |

官网首页不嵌入业务表单、服务模块卡片墙、个人待办、实时名额与资源可用性、业务运营统计或 Agent 聊天窗口。业务接口也要求登录及授权，不能仅通过页面跳转限制访问。

项目由一人开发，周期约一年；后端以 Java 为主，前端采用 Vue 3，官网拟使用 Three.js。校园品牌尚未命名，演示数据需明确标注为虚构数据。

## 2. 范围与完成标准

### 2.1 纳入范围

- 官网：品牌首页、学校概况、校园探索、新闻公告、校园文化、建筑介绍和公开内容搜索。
- 系统：活动与社团、场地与设备、校园办事、报修、课表与个人日程。
- 公共能力：身份权限、文件、消息、固定审批流程、审计和基础统计。
- Agent：有来源的知识问答、个人事务查询、活动及资源申请辅助，逐步扩展办事和报修辅助。

### 2.2 边界

- 课程表通过模板导入或后台维护，不包含选课、成绩、学籍和收费业务。
- 首期办事事项建议为请假申请、在校证明申请；证明结果为演示文档，不是有效学校证件。
- 使用站内消息和系统内提醒；短信、邮件及学校统一身份对接作为扩展。
- Three.js 首期为风格化校园外部场景，不包含整校精细复刻和室内漫游。
- 审批使用预定义流程及可配置的处理人员，不建设通用流程设计器。
- Agent 不自行决定审批结果，不替用户绕过规则，不直接修改数据库。

### 2.3 交付批次

批次决定开发顺序，不将后续批次模块排除出最终平台。

| 批次 | 交付内容 | 可演示成果 |
| --- | --- | --- |
| A | 账号权限、官网基本内容、活动、场地设备、固定审批、消息、日程、Agent 小规模验证 | 活动申请到报名的完整流程 |
| B | 社团成员、校园办事、报修、课表导入、3D 校园、Agent 正式接入 | 多角色校园业务与跨模块助手 |
| C | 统计、界面完善、异常恢复、性能验证、知识与任务评测、论文材料 | 可重复演示和验证的完整平台 |

“模块完成”要求：普通用户操作、后台处理、状态查询、必要的取消或拒绝分支、权限限制及相关通知均可运行。单独的列表和增删改页面不作为模块完成依据。

## 3. 角色与权限

### 3.1 角色定义

| 角色 | 主要职责 | 数据范围 |
| --- | --- | --- |
| 访客 | 浏览公开校园信息 | 已发布且标为公开的数据 |
| 学生 | 报名、预约、办事、报修、维护个人事务 | 自己的业务记录及获授权的公共数据 |
| 教师 | 使用服务、组织活动；获授权时参与审核 | 自己的记录、自己组织的活动及分配的审核记录 |
| 社团负责人 | 管理成员与社团活动 | 当前负责且有效的社团 |
| 校园服务人员 | 内容运营、资源管理、办事审批、维修处理等 | 按岗位及负责资源分配，职责不自动互通 |
| 系统管理员 | 用户、角色、配置和审计管理 | 管理权限范围；不自动拥有全部业务审批权 |

角色可叠加。“教师”身份不天然取得所有学生数据，“社团负责人”不天然取得其他社团权限。

### 3.2 权限矩阵

| 操作 | 学生 | 教师 | 社团负责人 | 服务人员 | 系统管理员 |
| --- | --- | --- | --- | --- | --- |
| 使用个人服务 | 本人 | 本人 | 本人 | 本人（按身份开放） | 本人（按身份开放） |
| 发起活动 | 首期不开放个人活动主办 | 本人组织 | 所负责社团 | 授权的校级组织 | 需单独授予组织权限 |
| 编辑社团与管理成员 | 否 | 被授权时 | 所负责社团 | 社团管理岗位 | 需单独授予业务权限 |
| 审核活动/预约/办事 | 否 | 被指定为审核人时 | 否 | 对应岗位与范围 | 需单独授予业务权限 |
| 处理报修 | 否 | 否 | 否 | 派单岗位或所分配维修人员 | 需单独授予业务权限 |
| 发布公开内容 | 否 | 否 | 社团内容提交审核 | 内容运营岗位 | 需单独授予业务权限 |
| 管理账号与角色 | 否 | 否 | 否 | 否 | 是 |

后端按动作、数据归属和当前状态共同校验；页面按钮隐藏不能代替权限验证。默认禁止审核本人发起的申请。

## 4. 功能需求目录

功能编号用于关联页面、接口、验收与论文，不代表实现顺序。

### 4.1 官网（WEB）

| 编号 | 功能 | 必须达到的行为 |
| --- | --- | --- |
| WEB-01 | 品牌首页 | 展示校园主视觉、学校简介、精选新闻公告与校园风采；各内容区限定展示数量，导航中设置统一校园服务入口 |
| WEB-02 | 新闻公告 | 分类、分页、检索、详情；仅展示公开且已发布内容 |
| WEB-03 | 校园文化与活动展示 | 展示经审核并公开发布的活动介绍、文化专题和成果；公开视图不暴露名额、报名名单、审批或其他办理信息 |
| WEB-04 | 社团风采 | 展示已审核社团、简介及公开活动；成员私人信息不公开 |
| WEB-05 | 校园设施介绍 | 建筑、设施、校园环境及公开开放说明；实时可用性、设备库存与预约入口位于工作台 |
| WEB-06 | 登录后服务指南 | 在工作台展示事项说明、材料、办理步骤、适用人群和规则更新时间；功能编号保留，页面归属调整为工作台 |
| WEB-07 | 官网搜索 | 仅检索公开且已发布的学校信息、新闻、文化活动、社团和建筑介绍；不搜索个人业务记录 |
| WEB-08 | 3D 校园探索 | 独立探索页面提供建筑选中、高亮、介绍卡和视角复位；首页可放校园视觉或探索入口，不承载预约与任务执行 |
| WEB-09 | 访问与降级 | 统一服务入口进入登录或已有会话的工作台；受限深链接登录后返回原服务；3D 失败使用建筑列表，导航可通过键盘访问 |
| WEB-10 | 学校概况 | 学校简介、办学理念、机构介绍等公开内容，独立栏目由后台维护，使用虚构校园资料 |

官网首页结构草案：顶部校名与导航 → 校园主视觉 → 学校简介 → 精选新闻 → 少量学校公告 → 校园风采 → 页脚。栏目条目数量由后续原型确定，不把全部系统功能堆放在首页。

### 4.2 身份与个人首页（IAM/HOME）

| 编号 | 功能 | 必须达到的行为 |
| --- | --- | --- |
| IAM-01 | 登录与账号 | 导入或管理员创建校园账号；不允许访客自行选择教师、管理员身份 |
| IAM-02 | 权限与停用 | 多角色、岗位范围、退出登录；停用或撤权后后续访问与 Agent 操作失效 |
| IAM-03 | 个人资料 | 修改允许修改的资料；身份与学工号由管理流程维护 |
| HOME-01 | 个人概览 | 我的申请、报名、预约、今日安排、未读消息和待办 |
| HOME-02 | 个人记录 | 分类查询、状态筛选、详情及可执行操作；其他用户记录不可访问 |

### 4.3 社团与活动（CLUB/ACT）

| 编号 | 功能 | 必须达到的行为 |
| --- | --- | --- |
| CLUB-01 | 社团入驻 | 提交资料、审核、拒绝理由、修改后重提；审核通过才公开 |
| CLUB-02 | 成员加入 | 申请、审核、撤回、退出；重复申请与重复成员受控 |
| CLUB-03 | 社团管理 | 简介维护、负责人移交、成员管理；重要变更留痕 |
| ACT-01 | 活动草稿 | 维护标题、主办方、时间、人数、地点、设备、简介、材料与报名条件 |
| ACT-02 | 活动申请 | 联动场地设备提交；条件不满足时返回具体原因，不产生半份申请 |
| ACT-03 | 活动审核 | 资源审核与活动审核串联；拒绝说明、撤回及修订重新申请 |
| ACT-04 | 活动发布 | 全部通过后主办方发布；审核过的关键字段变更需要重新审核 |
| ACT-05 | 活动报名 | 校验开放时间、资格、名额及重复报名；成功同步个人日程 |
| ACT-06 | 报名取消 | 截止前取消并释放名额；截止后可向主办方申请处理并记录原因 |
| ACT-07 | 活动签到 | 主办方生成限时签到码；报名用户在签到时段签到，允许有审计的人工补签 |
| ACT-08 | 活动结束 | 名单与签到统计、成果发布；取消活动通知参与者并更新日程 |

### 4.4 场地与设备（RES）

| 编号 | 功能 | 必须达到的行为 |
| --- | --- | --- |
| RES-01 | 资源目录 | 建筑、场地容量、设施标签、开放时段、设备数量和管理岗位 |
| RES-02 | 可用查询 | 按时间、人数、用途、设备筛选；区分可用、申请占用、已预订、维护 |
| RES-03 | 预约申请 | 个人预约与活动关联预约；提交时再次校验并发冲突 |
| RES-04 | 预约审核 | 审核人在职责范围内处理；拒绝、撤回、过期释放占用 |
| RES-05 | 使用与归还 | 登记场地使用、设备领用及归还；逾期进入待办，由服务人员跟进 |
| RES-06 | 取消与异常 | 使用前取消；活动关联预约需联动处理；资源临时停用通知受影响用户 |
| RES-07 | 资源维护 | 上下架、维护时间、设备损坏与修复；冲突的已确认预约不能静默删除 |

### 4.5 校园办事（SVC）

| 编号 | 功能 | 必须达到的行为 |
| --- | --- | --- |
| SVC-01 | 事项配置 | 两类首期事项、说明、材料清单、表单与处理岗位；采用预定义表单 |
| SVC-02 | 申请提交 | 保存草稿、材料上传、必填校验、提交、撤回与历史记录 |
| SVC-03 | 审核与补交 | 通过、拒绝、要求补交；补交后回到指定审核步骤，保留历史版本 |
| SVC-04 | 办理结果 | 查询结果及私有附件；请假审批通过后生成日程，在校证明生成演示文件 |

### 4.6 报修（FIX）

| 编号 | 功能 | 必须达到的行为 |
| --- | --- | --- |
| FIX-01 | 提交报修 | 故障类别、位置、描述、图片、联系信息；私有联系信息限相关人员访问 |
| FIX-02 | 分诊派单 | 服务人员补充信息、派单、改派、拒绝并说明；维修人员查看分配的工单 |
| FIX-03 | 维修处理 | 接单、处理中、完成反馈与材料；关键操作记录人员和时间 |
| FIX-04 | 确认评价 | 用户确认完成、退回继续处理、一次评价；未确认事项产生提醒，不自动伪造评价 |
| FIX-05 | 撤回与统计 | 派单前撤回，派单后申请取消；统计按类别、状态、处理时长汇总 |

### 4.7 日程与消息（CAL/MSG）

| 编号 | 功能 | 必须达到的行为 |
| --- | --- | --- |
| CAL-01 | 课表导入 | 提供模板、预览和错误行提示；确认后导入，按学期和周次展开 |
| CAL-02 | 个人日程 | 个人任务增改完成；业务日程链接来源，不能通过编辑日历绕过业务取消 |
| CAL-03 | 冲突检测 | 对重叠课表、活动和预约提示来源；个人时间冲突默认提示，不替代资源冲突硬校验 |
| CAL-04 | 业务同步 | 报名、预约、请假结果与取消同步；同一来源重复通知不生成重复日程 |
| MSG-01 | 站内消息 | 申请结果、派单、活动变更、预约异常、提醒；分类、未读数、详情跳转 |
| MSG-02 | 待办中心 | 从当前业务状态生成，处理后消失；消息历史不等同于待办 |
| MSG-03 | 消息偏好 | 可关闭一般提醒；必要办理结果与异常通知保留 |

### 4.8 内容、知识与管理（ADM）

| 编号 | 功能 | 必须达到的行为 |
| --- | --- | --- |
| ADM-01 | 内容运营 | 草稿、发布、撤下、归档、封面、公开范围和首页推荐；前台编辑内容不能注入执行脚本 |
| ADM-02 | 知识管理 | 文档上传、来源、版本、有效时间、可见范围、索引状态；撤下内容不继续参与新回答 |
| ADM-03 | 基础统计 | 活动参与、资源使用、申请处理和报修情况；说明口径和日期范围 |
| ADM-04 | 审计 | 查询关键操作的主体、对象、时间、结果；业务历史不能被普通编辑覆盖 |
| ADM-05 | 文件管理 | 类型与大小限制、访问授权；用户上传的私有材料不通过公开地址暴露 |

## 5. Agent 需求（AGT）

### 5.1 功能清单

| 编号 | 功能 | 验收要求 |
| --- | --- | --- |
| AGT-01 | 校园知识问答 | 登录后在工作台使用，给出有效来源链接及版本；资料不足时明确说明，不把生成内容当作校规 |
| AGT-02 | 个人事务查询 | 查询本人日程、待办和申请；每条可追溯到业务详情，不泄露他人材料 |
| AGT-03 | 资源与活动推荐 | 基于实时条件筛选并解释理由；数据不可用时不编造空闲场地 |
| AGT-04 | 活动申请辅助 | 追问必要条件、查询资源、生成可编辑草稿；用户确认后提交 |
| AGT-05 | 其他事务辅助 | 填写预约、办事和报修草稿；逐场景接入，材料和规则由系统校验 |
| AGT-06 | 执行与恢复 | 展示步骤、确认卡、状态和业务链接；工具失败可重试，不能宣称未成功的操作已完成 |
| AGT-07 | 会话管理 | 新建、历史、删除；草稿与业务记录独立保存，删除会话不取消业务申请 |

### 5.2 工具能力边界

| 工具组 | 允许的操作 | 约束 |
| --- | --- | --- |
| 知识查询 | 检索公开或获授权的规则与指南 | 过滤未发布、失效、无权限内容 |
| 个人查询 | 查询日程、申请、报名、预约、待办 | 当前登录人由服务端确定 |
| 资源查询 | 查询场地、设备和活动条件 | 展示查询时间，提交时重新验证 |
| 草稿生成 | 创建或更新个人申请草稿 | 标明尚未提交；不占用资源、不触发审批 |
| 业务提交 | 提交活动、预约、办事或报修 | 人工确认、权限与状态校验、重复调用保护 |
| 业务取消 | 撤回或取消明确的记录 | 人工确认且满足普通页面相同规则 |

Agent 页面、会话、查询、草稿和执行接口均要求登录，不提供官网匿名聊天。首期不开放审核、派单、用户授权等管理动作给 Agent。

### 5.3 确认与执行原则

- 用户看到确认卡：动作、对象、时间、主办方、资源、人数、关键材料、可能的关联影响。
- 确认与当前草稿版本绑定；关键字段变化或确认过期需要重新确认。
- 文档或用户输入中的“忽略权限”“直接审批”等文字不能改变工具权限。
- 工具只返回当前任务所需的数据，敏感材料不默认发送给模型。
- 执行期间凭证失效、权限变化、资源冲突时停止写入并说明原因。
- 网络超时但提交结果未知时，先按操作标识查询结果，再决定是否重试。
- 多步骤执行不能承诺全部成功；核心关联提交必须具备一致的业务结果，后续非核心失败单独报告。
- 不记录或展示模型内部推理；记录可读的动作、参数摘要和结果。
- 模型不可用时，保留常规页面办理能力。

## 7. 非功能要求

### 7.1 数据正确性

- 并发预约不能超额，活动报名不能超过名额。
- 活动及关联资源申请保持一致；拒绝、撤回和超时按规则释放占用。
- 相同操作重复提交不生成重复记录；修改有版本冲突提示。
- 消息发送失败不回滚已成功的业务，支持补发并避免重复消息。
- 关键历史保留：申请材料版本、审批意见、资源异常和 Agent 执行结果。

### 7.2 安全与可用性

- 身份、权限、数据范围、文件访问和关键业务操作由后端校验。
- 对登录、上传、模型请求等高成本接口设置合理限制。
- 私有联系方式、请假材料、报修图片与 Agent 会话按权限访问。
- 官网及工作台适配手机；管理后台优先桌面使用。
- 空数据、加载、失败、过期和无权限均有明确界面反馈。
- Three.js 不阻塞主要内容，支持暂停动画、低画质和设施列表回退。
- 演示环境可通过文档重建；使用虚构数据，不依赖校内不可访问接口。

### 7.3 可验证指标

以下为目标草案，正式测试前固定硬件、数据量和测试方法，并报告实测值。

| 项目 | 建议验证方式 |
| --- | --- |
| 常规 API | 记录常用查询与提交的 P95 延迟；参考目标为 50 并发用户下不超过 1 秒，模型调用及大文件操作单列 |
| 资源并发 | 多请求竞争同一场地时段、最后一件设备，不产生超额占用 |
| 报名并发 | 多请求竞争最后一个名额，成功记录最多一条 |
| 权限 | 直接访问其他人的申请、附件、Agent 工具，全部按规则拒绝 |
| 官网 | 在固定移动端网络条件下记录内容与 3D 加载时间，验证 3D 失败仍可完成核心导航 |
| Agent | 建立知识、查询、办理、失败和越权场景集，分别报告正确率、来源支持率、任务成功率和违规操作次数 |

## 8. 验收方案

每条需求验收包含：角色、初始数据、操作、业务结果、状态变化、消息/日程影响和异常分支。先采用人工演示和关键规则自动化验证结合的方式，测试方案随实现设计细化。

### 8.1 平台级演示

1. 管理人员发布内容，官网及搜索显示对应信息。
2. 主办方通过页面申请活动与资源，审核后发布；学生报名、收到通知、查看日程并签到。
3. 通过 Agent 完成相同申请路径，确认卡与最终记录一致。
4. 演示资源冲突、审核拒绝、撤回和活动取消，关联状态正确。
5. 学生办事与报修，服务人员处理，学生查询结果并确认。
6. 停用账号、跨用户访问、重复提交和 Agent 工具失败均得到正确处理。
7. 匿名访问只看到学校公开信息，业务页面要求登录，业务及 Agent 接口拒绝匿名调用；登录后官网仍保持学校展示形态。

### 8.2 核心流程详规

见[核心业务流程与验收 v0.1](./核心业务流程与验收-v0.1.md)，包括状态、默认规则、关键字段和具体验收案例。

## 13. 需求缺口评审

2026-09-30 对照现有五份文档进行评审。功能编号代表初始需求目录，官网调研与系统规划中的新增建议尚未全部合并，不能将当前编号数量当作最终冻结范围。

### 13.1 优先补齐的缺口

| 编号 | 当前状态 | 缺口与下一步 |
| --- | --- | --- |
| GAP-01 | 已列基础目录，缺少详细规则 | 明确学生、班级、学院、教师与部门关系，审核人如何分配，学期及身份失效后的业务处理；形成基础数据字典与权限实例 |
| GAP-02 | 教师以组织与审批为主 | 教师日常服务偏少；建议补充本人授课日程、面向所授班级的通知及资料发布，范围待纳入，不自动扩展为教学平台 |
| GAP-03 | 已有校园办事，只有两类事项 | 需要明确学生服务覆盖定位；宿舍、图书与学生发展作为独立候选估算，选定后补全流程，不能直接宣称已实现 |
| GAP-04 | 已有消息与发布，缺少定向规则 | 区分公开新闻、校内通知和私人办理结果；定义按学院、班级或活动成员分发，接收者、已读及撤下后可见性 |
| GAP-05 | 已有状态与异常原则 | 需要补齐任务超时后的催办、人员离岗改派、业务纠错与申诉入口；固定流程即可，不要求通用流程设计器 |
| GAP-06 | Agent 有工具边界与核心案例 | 需要逐工具定义输入、输出、错误、数据范围、确认条件、草稿版本与会话中断恢复；先固定三类重点任务 |
| GAP-07 | 官网与业务共享数据的原则已写 | 需要具体字段级公开视图，内容审核发布步骤、公开目录与内部资源的映射；防止发布业务对象时顺带泄露私有字段 |
| GAP-08 | 已有统计、审计和重建要求 | 补充数据库及私有文件备份恢复、批量导入报告、受控导出、知识索引重建、模型费用与请求失败监测 |
| GAP-09 | 有功能与页面清单，未形成原型 | 缺少角色页面树、关键交互和数据模型；明确正常、空、错误、无权限与取消界面后再设计接口 |
| GAP-10 | 有核心验收与性能目标草案 | 需要统一虚构校园设定和演示数据，建立需求—页面—接口—案例关联；现有验收原则需要落实为可重复验证的数据与步骤 |

### 13.2 建议完成标准

- 基础数据：用两个学院、多个班级、教师及部门构造样例，验证相同角色在不同归属下只能访问授权数据。
- 定向通知：向指定班级发通知，其他班级不可读取，接收人能看到通知来源和时间；私人办理消息不公开。
- 岗位转交：原处理人员离岗后按授权转交，旧人员后续不可办理，申请历史不丢失。
- 公开视图：官网能读取已发布活动介绍，不能读取报名名单、申请材料或实时内部资源数据。
- Agent 工具契约：至少覆盖活动联合申请、个人事务查询和校园知识问答；成功与失败均能追溯到明确数据。
- 备份恢复：在独立演示环境恢复数据与私有文件，核对关联关系、授权访问和基本业务可用性；知识索引可重建。
- 虚构校园设定：学校、学院、专业、校区、学期与规则引用一致，官网、系统和 Agent 不出现相互矛盾的口径。

以上为需求补全建议，正式功能编号和验收案例在下一版统一整理。

### 13.3 保留为选择项

宿舍、图书、学生发展及教师资料服务可提升校园覆盖，但须逐项确定实现范围。成绩、选课、学籍、校园卡充值、支付、门禁和心理健康业务涉及不同规则与数据，不因“综合服务”定位自动成为必做项。

下一轮应先合并已有调研、规划及本节缺口，形成统一的 v0.2 需求基线，标明已确认、建议新增和后续扩展，再开展角色页面树和核心原型设计。
