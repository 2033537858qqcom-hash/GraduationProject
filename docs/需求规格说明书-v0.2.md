## 1. 产品目标

构建以郑州工业应用技术学院为背景的综合服务平台，提供原创校园官网、学生与教师工作台、校园业务管理后台，以及能够查询信息和辅助办理事务的 Agent。2026-10-03 用户确定采用该真实学校，学校公开资料、品牌素材与演示业务边界见[学校背景与品牌基线](./学校背景与品牌基线-v0.1.md)。

官网按正式学校官网设计，以学校形象和校园信息展示为主。公开新闻、校园文化、社团和建筑介绍来自平台管理的数据。用户通过统一入口登录后进入独立业务工作台，办理结果同步至个人记录、日程和消息。Agent 使用同一套业务规则和数据权限，并且仅在登录后的系统提供。

### 1.1 已确认的官网与系统边界

官网首页不是全部模块的集合页。首页仅选取校园展示内容，各栏目拥有独立列表或详情页面。登录状态不改变官网的展示定位，个人事务始终在工作台呈现。

| 区域 | 访问条件 | 内容与操作 |
| --- | --- | --- |
| 学校官网 | 无需登录 | 学校概况、院系专业、教学科研、招生交流、校园生活及公开信息 |
| 登录入口 | 无需登录 | 统一身份登录及校园服务入口 |
| 业务工作台 | 登录后且具有对应权限 | 师生个人事务、教师资料与通知、住宿、报名、预约、申请、报修、日程、待办与 Agent |
| 管理后台 | 登录后且具有岗位权限 | 内容维护、审核、派单、资源、用户、统计与审计 |

官网首页不嵌入业务表单、服务模块卡片墙、个人待办、实时名额与资源可用性、业务运营统计或 Agent 聊天窗口。业务接口也要求登录及授权，不能仅通过页面跳转限制访问。

项目由一人开发，周期约一年；后端以 Java 为主，前端采用 Vue 3，官网拟使用 Three.js。学校名称确定为郑州工业应用技术学院，官网与系统共享学校身份配置；个人记录与账号需明确标注为演示数据。

## 2. 范围与完成标准

### 2.1 纳入范围

- 官网：精选首页、学校概况、院系专业、教育教学、科学研究、招生就业、合作交流、校园生活、信息公开、人群导航、校园探索和公开搜索。
- 系统：统一工作台与服务中心、活动社团、场地设备、校园办事、报修、住宿、课表日程、教师班级通知与课程资料。
- 公共能力：组织身份、数据权限、文件、定向通知、固定审批、反馈转交、审计、统计和运行维护。
- Agent：有来源的知识问答、个人事务查询、活动及资源申请辅助，逐步扩展办事和报修辅助。

### 2.2 边界

- 课程表通过模板导入或后台维护；本人已发布成绩、考试安排查询及受控数据维护按教学查询补充纳入。选课、学籍和收费业务仍不包含在当前范围。
- 首期办事事项建议为请假申请、在校证明申请；证明结果为演示文档，不是有效学校证件。
- 使用站内消息和系统内提醒；短信、邮件及学校统一身份对接作为扩展。
- 校园建筑及布局采用 Three.js，按核验资料建立校园外部场景，先完成资料充分的校区，再补齐另一校区；建模、交互及资料来源按[Three.js 校园探索设计](./Three.js校园探索设计-v0.1.md)执行，不包含整校精细复刻和室内漫游。
- 审批使用预定义流程及可配置的处理人员，不建设通用流程设计器。
- Agent 不自行决定审批结果，不替用户绕过规则，不直接修改数据库。
- 教师资料服务不包括作业批改、在线考试、成绩发布或排课优化。
- 住宿提供住宿记录、调整申请及人工确认入住，不包含自动排床、门禁和电费支付。
- 图书借阅、奖项申报和就业办理保留为扩展候选，不计入本版交付清单。
- 官网的招生、科研等栏目属于信息展示与内容管理，不自动扩展成录取或科研经费系统。

### 2.3 交付批次

批次决定开发顺序，不将后续批次模块排除出最终平台。

| 批次 | 交付内容 | 可演示成果 |
| --- | --- | --- |
| A | 基础目录、账号权限、服务中心、官网信息架构、活动、资源、审批、消息、日程、Agent 小规模验证 | 跨角色活动申请与报名闭环 |
| B | 官网完整栏目、社团、办事、报修、住宿、教师服务、定向通知、3D 校园、Agent 正式接入 | 师生与工作人员的日常校园服务 |
| C | 转交反馈、维护、统计、异常恢复、界面与性能验证、Agent 评测、论文材料 | 完整业务与可重复演示的系统 |

“模块完成”要求：普通用户操作、后台处理、状态查询、必要的取消或拒绝分支、权限限制及相关通知均可运行。单独的列表和增删改页面不作为模块完成依据。

## 3. 角色与权限

### 3.1 角色定义

| 角色 | 主要职责 | 数据范围 |
| --- | --- | --- |
| 访客 | 浏览公开校园信息 | 已发布且标为公开的数据 |
| 学生 | 报名、预约、办事、报修、维护个人事务 | 自己的业务记录及获授权的公共数据 |
| 教师 | 查看授课安排、发布资料与班级通知、组织活动，获授权时审核 | 自己的记录、本人授课班级、所属审核关系及组织活动 |
| 社团负责人 | 管理成员与社团活动 | 当前负责且有效的社团 |
| 校园服务人员 | 内容运营、资源管理、办事审批、维修处理等 | 按岗位及负责资源分配，职责不自动互通 |
| 系统管理员 | 用户、角色、配置和审计管理 | 管理权限范围；不自动拥有全部业务审批权 |

角色可叠加。“教师”身份不天然取得所有学生数据，“社团负责人”不天然取得其他社团权限。

### 3.2 权限矩阵

| 操作 | 学生 | 教师 | 社团负责人 | 服务人员 | 系统管理员 |
| --- | --- | --- | --- | --- | --- |
| 使用个人服务 | 本人 | 本人 | 本人 | 本人（按身份开放） | 本人（按身份开放） |
| 发起活动 | 首期不开放个人活动主办 | 本人组织 | 所负责社团 | 授权的校级组织 | 需单独授予组织权限 |
| 编辑社团与管理成员 | 否 | 被授权时 | 所负责社团 | 社团管理岗位 | 需单独授予业务权限 |
| 审核活动/预约/办事 | 否 | 被指定为审核人时 | 否 | 对应岗位与范围 | 需单独授予业务权限 |
| 处理报修 | 否 | 否 | 否 | 派单岗位或所分配维修人员 | 需单独授予业务权限 |
| 发布公开内容 | 否 | 否 | 社团内容提交审核 | 内容运营岗位 | 需单独授予业务权限 |
| 管理账号与角色 | 否 | 否 | 否 | 否 | 是 |

后端按动作、数据归属和当前状态共同校验；页面按钮隐藏不能代替权限验证。默认禁止审核本人发起的申请。

补充职责：教师只能向本人有效教学班发布课程资料或通知；辅导员是教师身份叠加的学生事务岗位，不等同于所有教师；宿管只能访问分配楼栋的住宿与调整申请；平台运维不自动拥有申请材料阅读权限。

身份有效期、学期、归属关系和账号状态分别管理。毕业归档保留业务历史，停止发起新申请；未归还设备、未完成住宿变更由授权人员处理，不能仅靠停用账号删除责任记录。

| WEB-09 | 访问与降级 | 统一服务入口进入登录或已有会话的工作台；受限深链接登录后返回原服务；3D 失败使用建筑列表，导航可通过键盘访问 |
| WEB-10 | 学校概况 | 学校简介、办学理念、机构介绍等公开内容，独立栏目由后台维护，采用经核验的学校公开资料并记录来源与更新时间 |
| WEB-11 | 院系与专业 | 学院目录、学院简介、专业与培养方向；目录关系一致，提供独立详情页 |
| WEB-12 | 教育教学 | 本科培养、公开师资、特色课程、教学成果，与登录后的教学班资料分离 |
| WEB-13 | 科学研究 | 研究方向、实验室、成果与学术动态，使用标注的演示资料 |
| WEB-14 | 招生与就业 | 招生介绍、专业资料、报考指南、公开通知及就业服务介绍，不执行录取 |
| WEB-15 | 合作交流 | 校企合作、交流项目与合作动态，展示有效公开内容 |
| WEB-16 | 信息公开 | 公开章程、制度、报告、联系渠道及私有材料隔离；文档明确演示性质 |
| WEB-17 | 人群导航 | 考生、学生、教职工、校友、访客的公开导航页；点击人群标签不授予角色 |

官网首页结构草案：校名、主导航与校园服务入口 → 校园主视觉 → 精选新闻 → 通知与学术信息 → 教学或科研特色 → 校园风采 → 页脚。首页不设考生、学生、教职工、校友和访客身份入口。栏目以独立页面呈现，不使用弹窗代替页面；避免重复面包屑和栏目标题，正文不提供“返回 XX”链接，用户通过导航手动切换。简介以独立栏目为主，首页只保留短文案或公开办学数据。各区展示数量在原型阶段确定。

公开搜索覆盖所有已上线公开栏目，不能检索校内通知、教学资料、个人申请或实时内部资源数据。公开内容采用独立视图及文件访问策略，不直接输出内部业务对象全部字段。WEB-06 保留历史编号，归属登录后服务中心。

| 我的事务查询 | 日期区间、类型、状态；不得指定其他用户身份 | 当前真实记录、状态、详情链接、查询时间；失败不能返回伪造事项 |
| 可用资源查询 | 明确日期、时间、人数和设备数量 | 候选及规则、查询时间；冲突、不可开放和查询失败可区分 |
| 草稿生成 | 业务类型、字段、来源记录版本 | 草稿标识、版本、缺失字段、摘要；尚未提交且不占用资源 |
| 确认后提交 | 草稿标识、版本、有效确认和操作标识 | 唯一业务记录、状态和链接；无权限、确认失效、规则不符、资源冲突、重复操作有明确结果 |
| 结果核实 | 操作标识或本人可访问业务标识 | 已成功、已失败或仍在处理中；未知结果不直接重复提交 |

接口编码与具体结构在接口设计阶段确定，但上述语义必须一致。操作标识与用户、业务动作绑定，不能用他人的标识查询结果或重放操作。

### 5.4 确认与执行原则

- 用户看到确认卡：动作、对象、时间、主办方、资源、人数、关键材料、可能的关联影响。
- 确认与当前草稿版本绑定；关键字段变化或确认过期需要重新确认。
- 文档或用户输入中的“忽略权限”“直接审批”等文字不能改变工具权限。
- 工具只返回当前任务所需的数据，敏感材料不默认发送给模型。
- 执行期间凭证失效、权限变化、资源冲突时停止写入并说明原因。
- 网络超时但提交结果未知时，先按操作标识查询结果，再决定是否重试。
- 多步骤执行不能承诺全部成功；核心关联提交必须具备一致的业务结果，后续非核心失败单独报告。
- 不记录或展示模型内部推理；记录可读的动作、参数摘要和结果。
- 模型不可用时，保留常规页面办理能力。

## 7. 非功能要求

### 7.1 数据正确性

- 并发预约不能超额，活动报名不能超过名额。
- 活动及关联资源申请保持一致；拒绝、撤回和超时按规则释放占用。
- 相同操作重复提交不生成重复记录；修改有版本冲突提示。
- 消息发送失败不回滚已成功的业务，支持补发并避免重复消息。
- 关键历史保留：申请材料版本、审批意见、资源异常和 Agent 执行结果。
- 一名学生至多有一个当前有效床位，同一床位不能同时有多份有效分配或预留；调宿切换具备一致结果。
- 通知接收者、资料访问范围与当前组织关系共同校验，原接收记录不自动赋予永久权限。

### 7.2 安全与可用性

- 身份、权限、数据范围、文件访问和关键业务操作由后端校验。
- 对登录、上传、模型请求等高成本接口设置合理限制。
- 私有联系方式、请假材料、报修图片与 Agent 会话按权限访问。
- 官网及工作台适配手机；管理后台优先桌面使用。
- 空数据、加载、失败、过期和无权限均有明确界面反馈。
- Three.js 不阻塞主要内容，支持暂停动画、低画质和设施列表回退。
- 演示环境可通过文档重建；学校公开资料记录来源，个人业务采用演示数据，不依赖校内不可访问接口。
- 校内通知、教学资料、住宿记录与导出文件与公开内容分开授权，过期链接不能继续下载。
- 备份与恢复只向运维岗位开放，备份本身按私有文件保护；恢复使用独立验证环境。
- 模型调用用量、成本与延迟单列；服务切换或故障不影响通过普通页面办理。

### 7.3 可验证指标

以下为目标草案，正式测试前固定硬件、数据量和测试方法，并报告实测值。

| 项目 | 建议验证方式 |
| --- | --- |
| 常规 API | 记录常用查询与提交的 P95 延迟；参考目标为 50 并发用户下不超过 1 秒，模型调用及大文件操作单列 |
| 资源并发 | 多请求竞争同一场地时段、最后一件设备，不产生超额占用 |
| 报名并发 | 多请求竞争最后一个名额，成功记录最多一条 |
| 权限 | 直接访问其他人的申请、附件、Agent 工具，全部按规则拒绝 |
| 官网 | 在固定移动端网络条件下记录内容与 3D 加载时间，验证 3D 失败仍可完成核心导航 |
| Agent | 建立知识、查询、办理、失败和越权场景集，分别报告正确率、来源支持率、任务成功率和违规操作次数 |

| 恢复 | 独立环境恢复后校验申请、占用、住宿与私有文件关联，并验证基本流程可继续 |

## 8. 验收方案

每条需求验收包含：角色、初始数据、操作、业务结果、状态变化、消息/日程影响和异常分支。先采用人工演示和关键规则自动化验证结合的方式，测试方案随实现设计细化。

### 8.1 平台级演示

1. 管理人员发布内容，官网及搜索显示对应信息。
2. 主办方通过页面申请活动与资源，审核后发布；学生报名、收到通知、查看日程并签到。
3. 通过 Agent 完成相同申请路径，确认卡与最终记录一致。
4. 演示资源冲突、审核拒绝、撤回和活动取消，关联状态正确。
5. 学生办事与报修，服务人员处理，学生查询结果并确认。
6. 停用账号、跨用户访问、重复提交和 Agent 工具失败均得到正确处理。
7. 匿名访问只看到学校公开信息，业务页面要求登录，业务及 Agent 接口拒绝匿名调用；登录后官网仍保持学校展示形态。
8. 教师向授课班级发布资料与通知，正确学生可访问，其他班级及离班用户不能访问。
9. 学生申请调整宿舍，相关人员审核安排，实际入住切换并发校验，取消或过期保留原住宿。
10. 岗位人员离岗，授权转交后新人员接续任务，旧人员不可处理；异议复核留有原始记录。
11. 演示导入错误报告、范围受控导出、独立恢复及知识重建，结果可核对。
