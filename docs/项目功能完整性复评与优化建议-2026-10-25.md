## 1. 总体判断

**当前项目已具备综合校园服务平台的主体，规模足以支撑本科毕业设计。主要办事流程已明显完善，但仍存在会导致流程无人处理或审核依据不一致的问题，尚不适合直接作为真实校园生产系统投入使用。**

本次结论分为三层：

| 评估口径 | 判断 | 原因 |
|---|---|---|
| 本科毕业设计的业务规模 | 已经足够，应进入范围收口和质量提升 | 官网、教学、五类办事、住宿、角色工作台、双校区探索及 Agent 已形成实际实现 |
| 当前已实现功能的完整性 | 主要路径可运行，异常与维护路径尚不齐全 | 正常审批到办结已有闭环；负责人变动、旧页面审批、资源新增和账号恢复等仍有缺口 |
| 原需求与实际交付的一致性 | 部分兑现，需要冻结验收范围 | 活动社团、统一日程、知识管理、定向通知等仍写在需求中，不能用相近入口替代完整实现 |
| 真实环境持续运行能力 | 仍待验收和建设 | 最新 MySQL 迁移、备份恢复、自动浏览器回归、全域责任交接尚缺完整证据 |

不提供笼统的完成百分比：原需求已经多次增补，当前没有统一验收分母。功能完整性也不能由菜单、接口或测试数量直接换算。

## 4. 本轮新增或进一步明确的问题

### R01：使用阶段的预约可以失去唯一负责人（P1，隔离 HTTP 复现）

复现过程：

1. 在独立 H2 库创建资源，配置唯一负责人，学生提交并审批通过。
2. 分别测试 `APPROVED`（已批准）和 `IN_USE`（使用中）记录。
3. 通过正式管理 API 解除唯一负责人，均返回 **HTTP 200**。
4. 原负责人继续登记使用/结束核销返回 **HTTP 403**。
5. 管理接口显示 `activeReviewerCount=0`，但 `pendingReviewCount=0`、`unattendedReviewCount=0`。

原因：解除关系检查、接任通知和无人办理统计都只覆盖 `SUBMITTED`。新增使用流程依赖当前资源负责关系，所以原先“只保证待审有审核人”的规则已不足。

影响：使用中的记录不能自行取消，也不会自动完成；失去负责人后，必须由管理人员主动发现并重新配置才能继续核销。已有“有效负责人为零”的信息，但缺少这些未完事项的统计和交接要求，不能说系统完全没有恢复手段。

证据：[管理统计](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:199)、[接任通知](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:276)、[解除关系](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:290)、[使用办理](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:1001)。

建议：统一定义需要负责人继续处理的状态，覆盖待审批、未结束的已批准预约和所有使用中记录；常规解除关系前指定合格接任人并通知全部相关阶段。紧急账号停用仍应立即生效，将遗留记录送入异常责任队列。

验收：逐状态检查解除、停用、撤权、接任、本人申请排除、接任通知去重；使用中即使超过结束时间，也必须有人能够完成核销。

### R02：旧页面审批可以批准退回后重新提交的新材料（P1，隔离 HTTP 复现）

复现过程：审核人读取 **2 人**申请的版本 0；另一操作退回申请；学生修改主题、人数为 **19 人**并重新提交，版本升为 2；随后发送原页面准备好的批准请求，仍返回 **HTTP 200，APPROVED**，批准的是新版 19 人申请。

原因：审批参数只有 `action/comment`，没有“审核人看到的版本”。后端虽然带数据库版本条件更新，但用的是请求处理时刚查询出的当前版本，只防止写入竞争，不能识别人的审核依据已经过时。

证据：[审批参数](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/ReservationDtos.java:110)、[后端审批](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:880)、[前端提交](D:/GraduationProject/frontend/src/pages/ReservationPage.vue:488)。

建议：前后端审批契约增加必填 `expectedVersion` 或对应字段，写锁内比较；不一致返回 409，刷新并明确展示材料变化，要求重新确认。预约编辑、撤回、取消和资源编辑也应按同一原则逐项核查，不能只让使用核销支持版本。

验收：双标签页、退回后补交、关键字段改变、重复提交审批；旧页面操作不得批准、拒绝或退回未重新核对的新版本。

### R03：预约资源管理缺少完整的新建和定位维护（P2，源码确认）

现有预约资源来自 V25 的预置数据；管理接口支持修改已有资源和负责人，没有发现新增预约资源的业务接口。修改字段仅含名称、容量、设备说明、规则、启停，不能配置新资源的校区、建筑、地点标识及详细位置。

因此，管理员能改既有记录，但新增西校区房间或另一个活动场地仍需要开发者改种子或数据库。这与教室资源管理已有新建能力不同。

证据：[预约资源控制器](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/ReservationController.java:48)、[修改字段](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/ReservationDtos.java:128)、[预置资源](D:/GraduationProject/backend/src/main/resources/db/migration/V25__venue_reservations.sql:98)。

建议：增加按授权范围创建资源、绑定校区/建筑/房间/地图地点、配置负责人、上线前完整性检查和变更审计。已有关联记录的资源采用停用、迁移流程，保留历史地点快照。

### R04：展示的资源规则还没有成为统一校验规则（P2，源码确认）

例如预置资源文字包含“提前 24 小时预约”“单次不超过 4 小时”，但通用服务校验只有开始时间不能早于现在、时长 30 分钟至 14 小时，没有对应资源的结构化提前量、最长时长或开放时间表。

这属于页面规则与机器校验未统一。本轮没有把所有文字规则逐条动态复现，也不把这些演示规则视为学校确认的制度。

证据：[资源说明](D:/GraduationProject/backend/src/main/resources/db/migration/V25__venue_reservations.sql:99)、[通用时间校验](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:336)。

建议：把可执行规则单独存储，例如提前量、可预约日期范围、开放时段、最长时长、维护窗口。界面说明、人工审核和 Agent 读取同一规则版本；仅供人工核实的要求应明确标注。

## 5. 仍需处理的跨模块缺口

### 5.1 账号的日常使用与岗位交接

未找到本人改密、管理员密码重置或首次登录改密接口。应补旧密码核验、受审计的临时密码重置、强制改密和凭据变更后的旧会话失效。可以先采用人工身份核验后的管理员重置，不必为此引入短信服务。

岗位方面，预约权限仍默认绑定 `STUDENT_AFFAIRS`，资源维护与学院事务职责尚未分开；基础账号修改只对部分领域提供保护，尚无全业务待交接清单。应区分“平台管理、学院业务、资源配置、具体资源办理”，按学院/校区/楼宇/资源分配范围。

必须保留已有保护：不是重新开放全权限管理员代办，而是让当前有资格的接任人承接具体事项。

证据：[认证入口](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/identity/AuthController.java:45)、[账号状态与保护](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/foundation/FoundationService.java:92)、[预约初始授权](D:/GraduationProject/backend/src/main/resources/db/migration/V25__venue_reservations.sql:89)、[既有预约交接验收](D:/GraduationProject/docs/预约责任交接补充验收-2026-10-17.md)。

### 5.2 物理资源与个人时间仍分散

教学课次和已发布考试已共用教室占用规则，预约则单独查询 `venue_reservation`。目前没有把 `classroom_resource` 与 `venue_resource` 绑定为同一物理房间的规则。

**如果同一物理房间分别录入两套资源，就不能保证教学和预约不冲突。** 这是代码确认的条件性风险，本轮没有声称发生了真实双重占用事故。

建议先统一校区、建筑和房间标识，建立课程/考试/预约/维护的共同占用校验。再增加只读个人日程聚合：课程、考试、请假、预约均链接原业务；取消或变更回原业务执行。个人时间重叠可以提示，物理资源冲突必须拦截。

证据：[教学占用集合](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/resource/RoomService.java:33)、[预约冲突](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:354)、[门户概览](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/portal/PortalController.java:37)。

### 5.3 Agent 的下一步应补知识维护与预约链路

当前指南按关键词匹配：读取前 100 条发布指南，排序后最多返回 3 条。它已有来源、版本和发布状态检查，但缺文档录入、有效期、可见范围、审核及重建后台。撤下失效控制已有基础，不能描述为完全没有知识约束。

“我的办事”页面聚合五类业务，Agent 的 `my_affairs` 工具仍限请假/证明，报修和住宿由各自工具查询；预约岗位待办可以聚合，但尚无完整的本人预约查询、可用场地查询和预约草稿工具。不能将“岗位待办中能看见预约”写成“Agent 已能办理预约”。

推荐顺序：

1. 知识后台：录入/来源/版本/有效期/可见范围/发布撤下，前台指南与 Agent 共用。
2. 补预约只读工具：按校区、人数、时段查找真实可用资源，再查本人进度。
3. 接入预约草稿预览和人工确认，调用已有业务校验；没有可用数据时明确说明。
4. 会话删除与业务记录分离，补管理端调用量、失败原因、耗时与用量视图。
5. 建独立于提示调试集的问法保留集，覆盖角色、资源变更、撤权、超时、拒答与恢复。

现有运行表已经记录工具、结果、耗时和 token，不应重复造日志；缺的是可以使用的管理视图与评测闭环。是否采用向量检索应由检索效果决定。

### 5.4 官网与三维校园应接通真实内容和具体业务

- `/content` 仍跳回首页；公开内容接口没有面向官网的分页和检索。学院名称为前端数组，入口主要去同一个招生网站，未形成项目内独立目录详情。
- 学校资料、章节和部分导航仍在代码中，CMS 编辑人员不能维护全部公开信息。
- 建筑详情预约按钮去通用预约页，未传当前地点。预约页其实已支持 `route.query.venue` 对应 `placeId` 筛选，应接通并保留登录回跳。
- 预约预置目录目前为东校区资源；西校区地图与模型的补充不能替代资源目录、负责人和开放规则的建设。

优先做“选择建筑 → 查看该建筑真实场地 → 可用时段 → 申请 → 审批 → 使用核销”。模型精度提升需要继续依据地图、校方资料或实测，不应为展示而虚构房间配置。
