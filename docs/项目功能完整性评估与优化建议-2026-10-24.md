# 项目功能完整性评估与优化建议

评估日期：2026-10-24。基线：`c1859fd` 及当前工作区已有修改。本次审查没有修改业务实现，也没有操作日常运行数据库。

> 后续交付：本报告记录的是本批开发前的审查基线。F01/F02 及 F04 中的返校销假、预约使用/结束与到期提醒已在后续批次实现，详见[闭环验收](D:/GraduationProject/docs/请假销假与预约使用闭环验收-2026-10-24.md)。其他缺口仍保留。

## 1. 总体判断

项目已经具备校园综合服务平台的主体：官网与内容管理、学生与教师门户、教学查询、请假、证明、报修、住宿、预约、多岗位工作台、消息以及带业务工具的 Agent。它已经超过“页面展示加简单增删改查”的程度。

**按本科毕业设计判断，业务规模已经足够；按现有需求文档判断，尚未全部兑现；按真实校园连续使用判断，还存在规则、流程收尾和运营维护缺口。** 这三个结论不能混成一个“完成百分比”。需求 v0.2 后续多次增补，当前也没有统一的验收分母，因此本次不编造整体完成率。

目前最值得投入的方向是：先修复预约规则，再补请假与预约的后半段流程，完善人员职责交接，最后强化知识管理与跨模块协作。继续增加独立菜单、特效或一个全新的大业务域，不会直接改善这些问题。

## 3. 本轮确认的问题与验收方向

### F01：预约人数没有按场地容量拦截——优先修复，已独立复现

- 复现：管理员把场地容量设置为 5；学生通过正式提交接口申请 6 人；接口返回 HTTP 200，状态为 `SUBMITTED`。
- 原因：提交时检查主题、联系方式、时段、启用状态及审核人，但未比较申请人数与场地容量。
- 证据：[VenueReservationService.java](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:625)。
- 建议：提交与审批共用服务端校验；规定容量为空、设备类资源、修改容量等场景的业务含义。前端同步提示，但不能只依赖前端限制。
- 验收：人数超过容量时不能提交或批准；容量在提交后降低，审核时重新核对；正数、边界值与资源类别均有测试。

### F02：场地停用后，待审申请仍能获批并下载凭证——优先修复，已独立复现

- 复现：先提交申请，再将场地停用，随后审批通过；审批仍返回 HTTP 200、状态 `APPROVED`，凭证下载也返回 HTTP 200。
- 原因：审批复查时段冲突，却没有复查场地是否仍启用；资源停用也未联动处理受影响申请。
- 证据：[资源修改](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:135)、[审批](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:888)。
- 建议：停用前列出受影响预约，允许明确取消、转场或保留特定已批准事项；停用期间不能继续批准新使用。凭证效力随真实业务状态变化。
- 验收：覆盖待审、已批准、使用中三种情况；申请人收到通知；旧凭证不能继续作为有效授权；重复操作保持一致。

### F03：预约和教学占用仍是两套资源规则——高价值整合，代码确认

- 预约冲突只查询 `venue_reservation`；教室占用查询课程与考试。`venue_resource` 与 `classroom_resource` 没有统一的房间关联。
- 这意味着：**若同一物理教室同时被建成教学资源和预约资源，当前机制不能保证跨模块互斥。** 本轮未构造真实重复场地记录，不将它描述为已发生的双重占用事故。
- 证据：[预约冲突](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/VenueReservationService.java:318)、[教室占用](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/resource/RoomService.java:34)、[预约表结构](D:/GraduationProject/backend/src/main/resources/db/migration/V25__venue_reservations.sql:1)。
- 建议：先统一物理资源标识，建立课程、考试、预约、维修停用的共同占用查询。保留各业务独立规则，不必重写成庞大的通用流程引擎。
- 验收：课程/考试占用的同一房间不能被预约；预约取消后释放占用；并发提交不能双占；跨校区同名房间不会混淆。

### F04：审批通过没有覆盖业务完成——需要补齐流程

- 请假目前批准后只有请假日程，缺少返校和销假；界面提示“已通过请假须另行申请变更”，但未找到对应变更链路。
- 预约状态止于草稿、提交、退回、批准、拒绝、撤回、取消，没有使用、归还、完成、过期等状态。借用设备目前主要是文字描述或整项资源，未形成多件库存领还。
- 证据：[请假动作](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/leave/LeaveService.java:116)、[预约状态](D:/GraduationProject/backend/src/main/resources/db/migration/V25__venue_reservations.sql:53)、[设备字段](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/reservation/ReservationDtos.java:8)。
- 最小方案：请假增加返校申报、销假处理、逾期提醒；预约增加使用确认、结束核销和过期未使用处置。若继续宣称“设备借用”，再补设备数量、领还及损坏记录。
- 验收：每条业务都有明确终态、当前责任人、下一步和异常出口；状态变化同步我的办事、岗位待办、消息与 Agent 查询。

### F05：权限已有细分，但岗位职责与交接不够一致——需要统一业务责任

- `STUDENT_AFFAIRS` 同时默认拥有预约审批和资源维护能力；V26 已移除 ADMIN 的默认资源维护权限，这是已完成的改进。学院学生事务岗位是否应维护全校场地，仍需重新明确。
- 基础账号停用已有辅导员负责班级与证明审核人的保护，但没有覆盖所有报修、住宿和预约待办的统一交接清单。单个领域的移交保护不能替代全域人员变更流程。
- 证据：[预约授权](D:/GraduationProject/backend/src/main/resources/db/migration/V25__venue_reservations.sql:94)、[岗位调整](D:/GraduationProject/backend/src/main/resources/db/migration/V26__venue_permission_refine.sql:14)、[账号停用](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/foundation/FoundationService.java:110)。
- 建议：区分系统管理员、学院事务人员、资源维护人员、具体场地审核人；按校区/学院/楼宇/资源配置范围。正常调岗显示待交接任务并指定接替人，紧急停用立即生效后将遗留任务转入异常队列，不能为了保留待办而强迫账号继续有效。
- 验收：调岗、离职、撤权、唯一负责人停用后，任务仍能被有权人员发现和接手，且不会被自动转交给申请人本人。

### F06：账号日常使用缺少改密与找回链路——基础功能优先补

- 检索身份与基础管理控制器，仅找到登录、身份查询、头像及账号创建/修改/启停；未找到修改密码、管理员重置密码等接口。
- 证据：[AuthController.java](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/identity/AuthController.java:45)、[FoundationController.java](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/foundation/FoundationController.java:14)。
- 建议：先实现旧密码验证后改密、管理员受审计重置、首次登录改密和凭据变更后的旧会话失效。短信找回可后置，不必引入付费短信作为前提。

### F07：Agent 已能办事辅助，但知识侧仍偏静态——最值得强化的特色能力

- 当前指南检索读取前 100 条已发布指南，通过关键词包含匹配排序，最多返回 3 条；这不是文档知识库管理或语义检索。
- 已记录调用结果、工具名、token 与耗时，因此不能说“完全没有观测”；缺的是管理员可用的统计、失败分析和知识维护流程。
- 会话接口有创建、读取、查询、任务及确认保存，未找到会话删除接口。
- 证据：[AgentGuides.java](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/agent/AgentGuides.java:16)、[调用记录](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/agent/AgentService.java:63)、[会话接口](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/agent/AgentSessionController.java:13)。
- 建议顺序：知识录入/来源/有效期/审核发布/撤下 → 检索评测与改进 → 管理员查看失败、耗时、调用量 → 预约查询与草稿辅助。是否引入向量数据库由检索效果决定，不先为技术栈增加复杂度。
- 验收：撤下或失效规则不再出现在新回答里；同义问题能找到正确指南；没有依据时说明资料不足；业务查询不越权；模型不可用时人工办理可继续；修改草稿后必须重新确认。

### F08：官网、3D 与业务的衔接还有提升空间——第二阶段优化

- 公开文章 API 有分类参数，但未提供面向官网的分页、全文检索；路由 `/content` 直接重定向首页，未形成完整新闻归档页。
- 学校名称、校训等资料部分固定在接口代码，栏目内容与服务入口也存在前端配置，不能全部交给内容人员维护。
- 3D 已有预约入口，预约目录也支持 `placeId`；目前建筑详情按钮未携带地点，进入预约页后需要重新找场地。
- 证据：[官网路由](D:/GraduationProject/frontend/src/router.ts:17)、[内容 API](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/content/ContentController.java:21)、[学校资料](D:/GraduationProject/backend/src/main/java/cn/zzuit/campus/campus/SchoolController.java:21)、[建筑预约入口](D:/GraduationProject/frontend/src/pages/CampusExplore.vue:437)。
- 建议：完善新闻列表/筛选/搜索、学院专业详情及资料来源维护；建筑跳转携带选中地点，并在登录后保留上下文。官网事实、办事指南和 Agent 引用同一已发布数据来源。

## 4. 原需求中尚未落地的范围

[需求规格说明书 v0.2](D:/GraduationProject/docs/需求规格说明书-v0.2.md:119) 包含活动社团、报名签到、统一个人日程、知识管理、定向通知、设备领还、官网栏目与公开目录管理、备份恢复等内容。这些不能因为已有相似名称的页面就标记完成。

需要正式冻结一版毕业设计交付范围：

- **优先保留并做深**：官网与 CMS、双校区探索、身份权限、教学信息服务、请假、证明、报修、住宿、场地预约、统一办事/消息/待办、Agent。
- **若活动社团仍写入开题报告或核心验收，就必须实现最小闭环**：组织者申请、审核发布、报名取消、签到、活动结束；否则明确列入后续规划，不能在论文中写成已实现。
- **后置扩展**：完整选课排课优化、财务缴费、图书流通、完整资产管理、真实校园统一认证，以及全校精确三维建模。是否建设取决于论文范围和可获取的数据接口。

还应将需求、路由、接口、角色、状态和测试组成一张交付矩阵，每项只用“已验收 / 已实现待验收 / 部分实现 / 规划中”四种状态。README 当前仍称 V24，并写“预约尚未实现”，与代码 V28 和已有预约功能不一致，须更新，避免答辩材料与实际演示矛盾。
