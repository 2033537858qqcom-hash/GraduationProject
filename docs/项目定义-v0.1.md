# 校园综合服务平台：项目定义 v0.1

本文件保留初始立项背景；当前具体范围以[需求规格说明书 v0.2](./需求规格说明书-v0.2.md)为准，文档入口见[文档索引](./README.md)。

状态：讨论草稿。已确认方向与建议范围分开记录，建议内容可随需求评审调整。2026-10-03 已确定学校为郑州工业应用技术学院，公开资料及演示数据处理见[学校背景与品牌基线](./学校背景与品牌基线-v0.1.md)。

## 1. 已确认的方向

- 本科毕业设计，由一人开发，计划周期约一年。
- 主题为校园综合服务平台，包含自行设计的官网、业务系统和 Agent。
- 后端以 Java 技术体系为主，业务前端采用 Vue 3。
- 用户已明确校园建筑及布局使用 Three.js；具体范围见[Three.js 校园探索设计](./Three.js校园探索设计-v0.1.md)。
- 以真实学校郑州工业应用技术学院为背景，学校公开资料采用核验来源，个人业务与账号使用明确标注的演示数据。
- 官网首页按正式学校官网设计，主要展示学校与校园信息；业务工作台独立于官网，核心操作和 Agent 必须登录后使用。
- 学校名称已确定；深蓝、白色、浅灰为项目视觉方向，学校标识与真实校园素材待核验，具体技术版本和学校选题要求尚未确定。

## 2. 项目定位与题目草案

题目草案：《基于 Java 与智能体的校园综合服务平台的设计与实现》。最终表述结合导师要求确定。

平台提供校园信息展示、校园事务办理与个人事务辅助。官网、用户工作台、管理后台共享业务数据，Agent 通过受控业务接口帮助用户查询信息与办理事务。

## 3. 产品结构（建议）

### 官网

- 首页：校园主视觉、学校简介、精选校园新闻、学校公告和校园风采，控制内容数量，栏目详情进入独立页面。
- 校园探索：风格化 3D 校园及等价的文字导航。
- 独立栏目：学校概况、校园新闻、学校公告、校园文化、校园探索；社团和活动作为校园文化内容展示。
- 公共内容可匿名浏览；官网通过统一的“校园服务 / 登录”入口进入系统。
- 官网首页不放预约、报名、申请、报修、个人待办、业务统计和 Agent 会话组件。登录用户访问官网时，官网也保持学校展示页面形态。
- 业务指南、实时可用资源、名额、业务表单与办理记录在登录后的工作台展示；官网仅展示经审核的公开介绍。
- Three.js 先验证一个场景，再按核验资料完成东、西校区布局与建筑选中、搜索及信息展示。重点建筑逐步细化，精细整校复刻、室内漫游暂不纳入必做范围。

### 用户工作台

- 个人首页：日程、消息、待办和常用服务。
- 活动与社团、场地与设备预约、办事申请、报修。
- 课表导入与个人日程，不承诺接入学校教务系统。
- Agent 会话及其产生的申请草稿、执行记录和结果入口。

### 管理后台

- 官网内容发布、用户与角色管理。
- 社团及活动审核、场地设备管理、办事审批、报修派单。
- 知识资料管理、基础统计、操作审计。
- 服务人员按职责访问对应业务，避免所有工作都集中给系统管理员。

## 4. 角色（建议）

| 角色 | 职责 |
| --- | --- |
| 访客 | 浏览公开信息 |
| 学生 | 报名、预约、申请、报修、管理个人日程 |
| 教师 | 使用校园服务，承担被授权的审核职责 |
| 社团负责人 | 管理本社团成员，组织活动 |
| 校园服务人员 | 按职责管理资源、审批申请或处理报修 |
| 系统管理员 | 管理账号、权限、平台配置与审计 |

一个账号可拥有多个角色，角色权限与数据归属共同限制访问。

## 5. 业务范围（建议）

| 模块 | 基本闭环 | 深度重点 |
| --- | --- | --- |
| 资讯与知识 | 编辑、发布、检索、归档 | 官网内容与 Agent 来源保持一致 |
| 社团与活动 | 入社申请、成员管理、活动申请、审核、发布、报名、签到、结束 | 名额控制、取消、活动与资源关联 |
| 场地与设备 | 查询、预约申请、审核、使用、归还、取消 | 时间冲突、维护状态、并发预约 |
| 校园办事 | 选择事项、提交材料、审核、补交、完成、撤回 | 首期仅支持两类事项，具体事项待确定 |
| 报修 | 提交、派单、处理、确认、评价 | 分工权限、状态流转、退回补充信息 |
| 学业与日程 | 导入课表、个人任务、业务日程同步、提醒 | 冲突提示；成绩、选课不在首期范围 |
| 公共能力 | 登录、权限、文件、消息、审批、审计 | 共用能力；首期审批采用固定流程 |

真实性能指标在明确运行环境和测试数据后制定，不预先宣称高并发能力。

## 6. Agent 范围（建议）

### 校园知识问答

检索已发布的校园规则与指南，附来源。没有依据时说明资料不足。文档内容作为检索数据，不作为工具执行指令。

### 个人事务查询

查询当前用户的活动、预约、申请和日程，汇总待办并解释冲突。所有调用由后端校验身份、权限与数据范围。

### 业务办理辅助

收集必需条件、查询资源、生成结构化草稿，用户确认后提交。首个完整场景为活动申请与资源预约。

- 修改、提交、取消操作需要可检查的确认界面。
- 确认后重新校验资源与业务状态，处理过期草稿和冲突。
- 重复调用不应产生重复申请。
- 工具失败时显示实际失败结果，不宣称任务已完成。
- 保存可读的执行步骤、工具结果摘要和业务记录关联，不展示模型内部推理。
- 常规页面与 Agent 共用业务服务及校验规则。

## 7. 优先打通的跨模块流程

1. 社团活动：准备活动 → 查询场地设备 → 生成申请 → 确认提交 → 审核 → 发布报名 → 日程同步 → 签到结束。
2. 报修：提交故障 → 派单 → 处理 → 通知用户 → 确认评价。
3. 个人事务：汇总课表与活动预约 → 提示冲突和待办 → 用户调整 → 更新日程。

活动审核与资源确认如何保持一致，应在流程设计中明确，不能分别成功后留下冲突记录。

## 8. 技术原则（建议，尚未锁定选型）

- Spring Boot 模块化单体，按业务划分模块。
- Vue 3 构建官网、用户工作台和后台，是否独立部署后续决定。
- MySQL 保存业务数据，文件存储、缓存、消息及检索组件按已验证需求加入。
- Java 服务接入模型与检索，并通过业务工具执行任务。
- Three.js 场景优先验证加载、建筑点击、移动端表现和文字导航回退。

## 9. 开发顺序

1. 需求评审：确定功能清单、角色权限、流程和验收标准。
2. 小规模验证：3D 建筑交互，以及 Java Agent 调用受控查询接口。
3. 原型与数据设计：官网视觉、用户任务路径、后台页面、核心实体与状态。
4. 建立项目骨架，先实现活动—资源—审批—日程的闭环。
5. 扩展其余业务，接入 Agent 写操作并处理异常。
6. 完成联调、验证、演示数据、论文和答辩材料。
