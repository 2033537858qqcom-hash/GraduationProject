## 1. 交付行为

### 预约负责人覆盖全部未完成阶段

统一需要负责人继续处理的范围：

| 状态 | 是否需要继续交接 | 原因 |
|---|---|---|
| SUBMITTED | 是 | 尚需审批 |
| APPROVED 且批准时段尚未结束 | 是 | 尚需登记使用或处理后续事项 |
| IN_USE | 是，包含已经超时的记录 | 必须由有资格人员核对交接并结束核销 |
| APPROVED 且时段已结束、未登记使用 | 否 | 由既有到期任务标记过期，不要求人工认定实际使用 |
| COMPLETED、CANCELLED、REJECTED、EXPIRED 等 | 否 | 保留历史，不阻止正常岗位调整 |

解除负责关系前，在共享写锁内检查剩余人员的当前资格、启用状态及非申请人身份。会留下无人办理记录时返回 `409 REVIEWER_HANDOFF_REQUIRED`。先添加接任人员，再解除原负责人。

接任人员会收到现有待审批、待使用和使用中的通知；重复添加不重复发送，不通知其接手自己的申请。原负责人解除后不能继续查看或办理原场地申请。

紧急停用或撤权继续立即生效；资源配置页显示失效关系和遗留事项，允许管理人员配置接任者。本批扩展的是预约领域，不代表已建设覆盖所有业务的异常责任队列。

### 审核必须与人看到的材料版本一致

预约审批请求新增必填非负 `version`。缺失、null 或负数返回 400；不与当前版本一致时返回 `409 RESERVATION_VERSION_CHANGED`，不新增审批动作、不改变申请状态。通过、退回、驳回三种动作均校验。

前端在打开确认框之前保存申请编号、版本、动作和意见，确认后提交该快照。收到版本冲突后重新读取最新详情、清空旧意见，并明确显示“本次决定未执行”，要求重新核对和填写意见，不自动重试原决定。

同一版本重复审批也不会生成第二次审批记录。现有权限、负责范围和禁止自审规则继续执行。

## 2. 接口与管理页

`POST /api/reservations/{id}/review`：

```json
{"version": 2, "action": "APPROVE", "comment": "已重新核对人数与场地使用方案"}
```

`GET /api/reservations/venues/manage` 保留原 `pendingReviewCount`、`unattendedReviewCount` 的待审批含义，增加：

- `pendingUsageCount`：未结束的已批准预约数。
- `activeUseCount`：使用中预约数，包含超时未核销。
- `unattendedTaskCount`：所有需继续办理但没有有效非申请人负责人的记录数。

管理卡片和负责人弹层同步展示三个阶段的数量，以及无人办理总数。管理接口只返回数量与负责关系，不因此暴露申请详情；查看申请仍需当前具体资源负责关系。

本批没有数据库结构变化，继续使用 V31。前后端需要同步更新，旧客户端省略 `version` 的审批请求会被拒绝。

## 3. 回归范围

新增 `ReservationConsistencyIntegrationTest`，共 17 个实际执行案例：

- 待使用、使用中解除唯一负责人受到保护；接任后可解除，原负责人失去访问权，接任人可核销。
- 两个阶段分别验证停用账号、撤销审批岗位后的无人办理统计与接任恢复。
- 接任通知覆盖三个阶段，重复添加不重复通知，本人申请不路由给本人。
- 不能把申请人本人作为唯一剩余负责人。
- 已结束时段的未使用批准记录和已核销记录不阻止解除关系。
- 退回补交后，旧版通过、退回、驳回均拒绝；重新核对最新版后可执行。
- 缺少、null、负数版本不能审批。
- 重复决定不新增历史。

原有三组预约、责任与闭环集成测试同步提供显式版本。定向 46 项全部通过。

测试先于业务修改：初始 17 项中 16 项按预期失败、1 项原本通过；修复后同一目标 17 项全部通过。失败与成功日志保存在 `output/reservation-consistency-2026-10-25/`。
